# Game-UX Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/game-ux/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **ゲーム向けヒューリスティック評価は汎用リストでなくゲーム特化リストで実施する** (gux-p-001): NielsenのWeb/SaaS向け10ヒューリスティックだけでなく、Federoff・HEP・Nokia・Schafferなどゲーム特化のヒューリスティックリストから自分のプロジェクトに合うものを選ぶ。
- [ ] **ゲームUIヒューリスティック：一貫性・フィードバック・プレイヤー制御感・初回体験を軸に評価する** (gux-p-002): ゲーム内・ゲーム間（プラットフォーム慣習）双方で操作やメニューの一貫性を保つ。
- [ ] **ユーザビリティ問題は深刻度4段階＋未分類で分類し、修正提案とスクリーンショットを添えて報告する** (gux-p-003): 問題をminor（軽微）／moderate（中程度）／important（重要）／critical（致命的）の4段階に分類し、開発チームが着手順を判断しやすくする。
- [ ] **アクセシビリティ機能（色覚・字幕・入力リマップ）は設計段階から組み込む** (gux-p-004): 画面設定で色覚特性に配慮したカラー変更を可能にする。
- [ ] **入力デバイスの触感とナチュラルマッピングでゲームフィールの手応えを設計する** (gux-p-005): 入力デバイス自体の物理的な触感（重さ・質感）がゲームの感触評価に影響することを認識し、想定コントローラでのプロトタイプ検証を行う。
- [ ] **外部表象（注釈・状態トラッキング）でプレイヤーの認知負荷を肩代わりする** (gux-p-006): 人はショッピングリストのように、頭で覚える代わりに外部表象（メモ・チェックリスト・並べ替え）へ情報を逃がす『注釈（annotating）』『認知的トレース（cognitive tracing）』を自然に行う。この仕組みをUI・HUDに取り込む。
- [ ] **インターフェースの評価軸は『プレイヤーが自分の体験をコントロールできているか』に置く** (gux-p-007): インターフェースの目的は『見た目の良さ』ではなく、プレイヤーに『自分が体験をコントロールできている』と感じさせることだと位置づける。
- [ ] **フィードバック手段は音・アニメーション・色変化・テキスト変化を組み合わせ、単一チャンネルに依存しない** (gux-p-008): ボタン押下やゴール達成などのアクションに対し、音（クリック音・効果音・ジングル）でフィードバックする。
- [ ] **常時表示HUDでなく、必要な瞬間だけ出て消える一時的HUDや環境内手がかりで没入感を守る** (gux-p-009): アイテム取得やダメージなどのイベント発生時だけHUDをポップさせ、一定時間操作がなければ画面外へスライドして隠す（Crash Bandicootの例）。
- [ ] **プレイテストは対象範囲を絞り、設計者はプレイに参加せず観察・記録に徹する** (gux-p-010): 1回のプレイテストで検証する機能・レベルは1〜2個程度に絞る。
- [ ] **ゲームフィールの『Context』：空間的制約の密度が操作の手応えの快・不快を決める** (gux-p-011): 移動能力を実装したら、白紙の空間ではなく足場や障害物などの空間的コンテキストを早期に用意し、動きの意味を判断できるようにする。
- [ ] **UIはワイヤーフレーム→インタラクティブプロトタイプで検証してから最終ビジュアルに着手する** (gux-p-012): 最初にフローチャートと簡易なスケッチでUIの構造を設計し、次に低コストなツール（Flash・Figma・Balsamiq・Adobe XDなど）でクリックスルー可能なプロトタイプを作って画面遷移や操作フローを検証する。
- [ ] **触覚フィードバックは常時提示にせず、要所を絞ったタイミング・強度で設計する** (gux-p-013): 触覚フィードバックは『いつ・どこに・単発かパターンか・強度』を設計変数として個別に決め、伝えたい情報の重要度に応じて頻度を絞る。
- [ ] **序盤数十秒のプレイ自体を『マニュアル不要』のチュートリアルとして設計する（Gamenics第二原則）** (gux-p-014): ゲーム開始直後の30〜60秒程度のプレイ区間に、基本操作（移動・攻撃・アイテム取得など）を体験しながら覚えられる状況を意図的に配置する（例: Super Mario Bros.冒頭のクリボー遭遇とブロック破壊）。
- [ ] **HUD/画面遷移は安全フレームとボタン押下数の上限を設計指針にする** (gux-p-015): 重要なHUD情報は画面端の『safe frame』の内側に収め、画面のクロップやオーバースキャンで欠けないようにする。
- [ ] **プレイテストは段階的な信頼度で回す：メンター／友人家族／ベータの三段階** (gux-p-016): プレイ可能な実装がまだない構想段階では、経験豊富なデザイナー・メンターに設計案そのものをレビューしてもらい、高レベルの設計欠陥を早期に潰す。
- [ ] **プレイ内アンケートは頻度・タイミング・文脈メタデータを設計し、行動ログと組み合わせて解釈する** (gux-p-017): 行動データだけに頼らず、要所でゲームを一時中断し短い設問を出す『イベント発生時アンケート』（ミッション完了・死亡・パズル解決など）を併用し、主観的な評価を対応づけて記録する。
- [ ] **UI配置はインターフェースの没入度分類・グリッド・Fitts法則・デバイス特性で設計する** (gux-p-018): UI要素が『ゲーム内キャラクターも認識している情報か（diegetic/meta）』『プレイヤーだけが見ている情報か（spatial等）』を区別し、没入感をどこまで優先するかに応じて表現方法を選ぶ（例: 車のダッシュボードの速度計はdiegetic、キャラが意識していない敵の狙い先を示す矢印はspatial）。
- [ ] **チャレンジとスキルの釣り合いを継続的に観測し、フローチャンネル（緊張と緩和のサイクル）に留める** (gux-p-019): Csikszentmihalyiの『フローチャンネル』（挑戦と技能がともに高まりながら釣り合っている状態）を目標に、レベル・敵の強さ・報酬（より強い武器等）を段階的に釣り合わせる『緊張と緩和』のサイクルで難易度を設計する。
- [ ] **インターフェースに『ジューシーさ』（継続的フィードバック・二次モーション・複数同時報酬）を持たせる** (gux-p-020): プレイヤーの操作から連続的に発生する『二次モーション（second-order motion）』（プレイヤーの入力から派生して起こる追加の動き・演出）を用意し、少しの操作で持続的な心地よいフィードバックの流れを生む。
- [ ] **パズルはまず目的（ゴール）を曖昧にせず明確に伝える** (gux-p-021): パズルを設計・レビューする際は、複雑さや意外性より先に『プレイヤーはこのパズルの達成条件を見ただけで理解できるか』を確認する（Puzzle Principle #1: ゴールの明確さ）。
- [ ] **プレイテスト冒頭のウォームアップとフレーミングで『ゲームを測っている、あなたを測っていない』を明示する** (gux-p-022): セッション冒頭に5分程度のウォームアップ会話（普段遊ぶゲームの種類・好きな理由・情報収集先など）を設け、緊張をほぐしつつ被験者の背景（プレイヤー属性）を把握する。
- [ ] **感情ホイール（Plutchikなど）をパレットとして使い、場面ごとに狙う感情の組み合わせを設計する** (gux-p-023): Plutchikの感情ホイールのような、隣接・非隣接の感情の組み合わせを見渡せるツールを使い、あるシーン・場面で狙う感情（例: 静けさと物思いのような隣接感情の組み合わせ）を意図的に選ぶ。
- [ ] **アイコン操作は即時フィードバックとラベル表示を用意し、通貨/リソース表示は将来の桁数まで見込んで設計する** (gux-p-024): アイコンにカーソルを合わせたら名前・効果をラベル表示し、選択・クリック時には色変化やクリック音などその場で分かるフィードバックを必ず返す。
- [ ] **実行できない操作はグレーアウトで明示し、誤操作を未然に防ぐ** (gux-p-025): 現在の状況で実行できないメニュー項目・ボタンは、文字やアイコンをグレーアウト（減色・低コントラスト化）し、視覚的に『今は選べない』ことを一目で伝える。

## アンチパターン（該当していないか）

- [ ] **ヒューリスティック評価をユーザーテストやデザイン標準と混同しない** (gux-a-001): ユーザーテストでは実際のユーザーに自然にプレイさせ、評価者はヒューリスティックを使わずに観察する。ヒューリスティックを使った分析はユーザー自身にさせない。
- [ ] **発話思考法（think-aloud）をゲームの『面白さ』評価にそのまま流用する** (gux-a-002): インターフェースの操作性（ボタンの発見しやすさ等、機能的な使いやすさ）を検証する目的では、think-aloudをこれまで通り使ってよい。
- [ ] **不慣れな新プラットフォームの目新しさを追いかけ、コアループの磨き込みを後回しにする** (gux-a-003): プロジェクト開始時点で、コアとなる行動（コアループ）が『それ単体で面白いか』を、使い慣れた技術基盤・簡易な実装でまず検証する。
- [ ] **ミラーの『7±2』を『UI項目は7個までにすべき』という設計制約に誤って転用する** (gux-a-004): Millerの理論は『新しく提示され記憶しておく必要がある項目の数』についての知見であり、画面上に常時表示されて参照できる項目の数の上限を直接規定するものではないと理解する。

## トレードオフ（明示的に判断したか）

- [ ] **ユーザビリティ手法の選定は必要資源（時間・専門性・機材）と得られる情報の粒度のトレードオフで決める** (gux-t-001): 同種のゲームを多数開発するスタジオでは、デザイン標準の策定（委員会・研修・運用コスト大、事前準備が必要）に投資する価値がある。
- [ ] **ラボでのユーザビリティテストとin-the-wild調査は『制御』と『生態学的妥当性』のトレードオフ** (gux-t-002): 特定の場面や操作を細かく観察したい場合はラボテストを使う。常に評価者やカメラが立ち会えるため、狙った事象を確実に記録できる。
- [ ] **体験版・トライアルのコンテンツ量は『魅力の訴求』と『本編購買意欲の維持』のバランスで決める** (gux-t-003): トライアルの目的（ゲームの『クール』で興味深い要素を見せる、本編がどんな感じかを伝える）を明確にしてからコンテンツ量を設計する。
- [ ] **サプライズ・ランダム性の演出量は『驚きの快感』と『プレイヤーの選択が意味を持つこと』のトレードオフで調整する** (gux-t-004): 予想外だが受け入れられる結果（想定より大きな報酬など）を適度に配置し、プレイヤーの再エンゲージメントを誘発する。
- [ ] **Easy Funは新奇性と親近感のバランスで維持される（新奇すぎても既知すぎても離脱を招く）** (gux-t-005): ロールプレイ・曖昧さ・ディテール・アイコン的状況などのEasy Fun要素を組み合わせ、プレイヤーの想像力を刺激する。
- [ ] **F2Pの収益化フレーミングは『アイテムを売る』か『機会・冒険を売る』かで挫折感が変わる** (gux-t-006): 攻略に必要な強化アイテムそのものを売ると、プレイヤーは『詰まったから課金させられた』という敗北感・失敗感を抱きやすい。
- [ ] **フィードバックループ設計：強化ループ（rich-get-richer）とバランシングループ（ラバーバンディング）のトレードオフ** (gux-t-007): コア体験として『上手い人がさらに有利になる』手応え（強化ループ、例: Monopolyの資産で家賃収入が増える）を採用する場合、それがゲームの魅力の中心であることを明確にし、下位互換として敗者への『詰み』感（feel bad）を許容できるか判断する。
- [ ] **ゲーム内で標準化すべき範囲：コンテナ（操作体系・HUD）は一貫性、コア体験は独自性・没入を優先する** (gux-t-008): 『コンテナ』にあたる部分（HUDの配置、メニュー操作、アクションと入力デバイスの対応付けなど）は一貫性のある標準に寄せ、プレイヤーが操作方法を推理し直す必要をなくす。この部分は『消えている（意識されない）』ほど成功と考える。
- [ ] **生理指標計測 vs 自己申告：感情強度の客観捕捉と装着・体動制約のトレードオフ** (gux-t-009): 『いつ・どれくらい強く』感情が動いたかを連続的かつ客観的に把握したい場合は、GSR（皮膚電気反応）や心拍数などの生理指標を検討する。特にPTSD治療用ゲームのように、体験の強度を治療域に保つ必要があるケースでは、生理指標が自己申告より適した調整手段になる。
- [ ] **プロトタイプの堅牢性 vs 変更しやすさ、高忠実度 vs 低忠実度のトレードオフ** (gux-t-010): 初期の意思決定段階では低忠実度（紙・簡易モック等）のプロトタイプを使い、変更コストを最小に保ったまま多くの代替案を試す。
- [ ] **シールド/ブロックは壊れる仕様か恒久仕様かで、回避重視かブロック活用重視かの立ち回りが変わる** (gux-t-011): 盾を『壊れる限定資源』にすると、プレイヤーはそれを温存しようとして使用を控え、結果的に回避・ジャンプなど他の手段に頼る傾向が強まる。ブロック活用そのものをゲームプレイの中心に据えたい場合はこの設計を避けるか、リソースを十分に補充できる導線を用意する。
