# Performance Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/performance/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **プロファイリング駆動で最大ボトルネックから最適化する** (perf-p-001): 最適化の前に必ず仮説を立て、プロファイラで計測してボトルネック（大量のディスク読み取り、ロック競合、メモリリーク、超高頻度呼び出し関数など）を特定する
- [ ] **「十分速い」を定義して最適化の止め時を決める** (perf-p-002): 世界最速ではなく「自分のニーズに対して十分速く・十分に省リソース」を目標として明文化する
- [ ] **CPUプロファイリングはタイマーベースの低頻度サンプリングで行う** (perf-p-003): タイマーベースのサンプリング（CPUあたり99Hz程度）を既定にする。イベント頻度が既知なのでオーバーヘッドが予測可能
- [ ] **フレームグラフでプロファイルを可視化し、カーネル・ユーザー両スタックを取る** (perf-p-004): CPUプロファイルはフレームグラフに集約し、ミックスモードプロファイルで注目点を特定する
- [ ] **レイテンシとスループットは必ずペアで評価する** (perf-p-005): 性能を「レスポンスタイム」と「スループット」の2側面で常に対にして定義・計測する
- [ ] **レイテンシを共通単位にして問題を定量化し、改善上限を見積もる** (perf-p-006): 異なる種類の処理はすべて時間（レイテンシ）に換算して比較し、要因除去時のスピードアップ上限を計算する
- [ ] **レイテンシの計測点を明示し、ユーザー視点のエンドツーエンドを基準にする** (perf-p-007): レイテンシには常に修飾語（DNS解決、TCP接続、要求、TTFB等）を付け、ユーザー側からの計測を最優先にする
- [ ] **使用率だけでなく飽和度（キュー長・待ち時間）を監視する** (perf-p-008): リソースが処理できる量を超えた要求（飽和度）を、使用率と別の指標として監視する
- [ ] **平均ではなく分布・パーセンタイル・外れ値でレイテンシを評価する** (perf-p-009): レイテンシはパーセンタイル（p95/p99等）やヒストグラムで把握し、平均は補助指標に留める
- [ ] **ワークロード特性を把握し、不要な処理を削る** (perf-p-010): 要求の属性を集計してワークロード特性を把握し、削減・排除できる処理を探す（最速のクエリは実行しないクエリ）
- [ ] **負荷を段階的に増やして変曲点（スケーリング限界）を特定する** (perf-p-011): 最小負荷から徐々に上げ、応答時間・スループット・エラー頻度の推移から効率が低下し始める変曲点を特定する
- [ ] **CPUキャッシュ階層とメモリ局所性を意識して設計する** (perf-p-012): メモリアクセス速度が性能を支配し得る前提で、CPUアフィニティ・NUMA局所性・キャッシュ効率を活かす設計にする
- [ ] **管理的な処理は初期化時に前倒しする** (perf-p-013): 事前計算・メモリ確保・設定読み取りは初期化時に一度だけ行い、ホットパスの流れを中断させない
- [ ] **本番は可観測性ツール、ベンチマークは隔離環境で使い分ける** (perf-p-014): 本番ではまず可観測性ツールで観察し、実験・負荷ツールはアイドルなテスト環境で使う
- [ ] **分析クエリは実行プロファイルを確認し、スキャン削減策を適用条件付きで選ぶ** (perf-p-015): 実行プロファイルでプルーニング・キャッシュ・スピルを確認してから、条件に合う最適化機能を選ぶ
- [ ] **GPUオフロードはデータ転送コスト込みでCPUベースラインと比較して判断する** (perf-p-016): まずCPU構成でレイテンシ・スループット・コストのベースラインを取り、GPU化の効果はその差分で評価する
- [ ] **地理的分散配置でユーザー近接のレイテンシを削減する** (perf-p-017): グローバルなユーザーベースには複数リージョン展開で地理的に近い拠点から応答する
- [ ] **実行プロファイルに基づくコンパイル最適化（PGO/JIT）を活用する** (perf-p-018): 本番相当ワークロードのプロファイルを入力に再コンパイル（PGO）し、JITランタイムの実行時最適化を信頼する

## アンチパターン（該当していないか）

- [ ] **ランダム変更アンチメソッド（当てずっぽうチューニング）** (perf-a-001): 変更の前に、なぜその項目が問題なのかの仮説と根拠（計測データ）を用意する
- [ ] **プロファイリングせずに直感でボトルネックを修正する** (perf-a-002): コード構造を変える前に、仮説を定義してプロファイリングで裏取りする
- [ ] **平均値・全体集計だけで性能を判断する** (perf-a-003): ダッシュボードの主要グラフをパーセンタイル・ヒストグラム系に置き換えるか併記する
- [ ] **スループット目標なしのレイテンシテスト** (perf-a-004): レイテンシテストには必ず目標スループット（想定QPS）を併せて定義する
- [ ] **キャッシュありき設計でキャッシュ障害時の性能を検証しない** (perf-a-005): キャッシュを経由せず永続ストアへ直接読み書きした場合の性能を定期的に測定しておく
- [ ] **本番環境で高オーバーヘッド計測・ベンチマークを実行する** (perf-a-006): 本番での調査は低頻度サンプリングなど、オーバーヘッドが予測・制御可能な手段に限定する
- [ ] **コンテナ内で従来ツールの数値を鵜呑みにする** (perf-a-007): 各ツールがコンテナ内で「ホストの値」と「コンテナの値」のどちらを表示するかを把握してから読む
- [ ] **インデックス的な最適化機能の無差別適用** (perf-a-008): 補助構造は、クエリで実際に頻用されるカラムに絞って追加し、効果を検証する

## トレードオフ（明示的に判断したか）

- [ ] **レイテンシ vs スループット（バッチ化・多層処理）** (perf-t-001): ユースケースごとに「1件の応答時間」と「単位時間の処理量」のどちらが価値かを明示してからバッチ化・集約の粒度を決める
- [ ] **レプリケーション方式：非同期・同期・準同期** (perf-t-002): レイテンシ優先なら非同期、耐障害性優先なら同期、中間なら準同期を、データ損失リスクと書き込み速度の兼ね合いで選ぶ
- [ ] **キャッシュ導入：レイテンシ削減 vs 運用複雑性・整合性リスク** (perf-t-003): レイテンシの利得と、コンポーネント追加の運用コスト・障害リスク・整合性リスクを並べて評価する
- [ ] **中間層（プロキシ・イベントストア）の追加：機能 vs レイテンシ** (perf-t-004): 処理レイヤの深さとレイテンシの関係（L4は低遅延、L7は高機能だが遅延大）を評価し、シンプルさを優先する
- [ ] **低レイテンシOSチューニング vs 消費電力・省電力機構** (perf-t-005): 低レイテンシ要件のホストでは、消費電力増を代償に決定的な性能を優先するプロファイルを適用する
- [ ] **サンプリング vs トレーシング（精度 vs オーバーヘッド）** (perf-t-006): 常用・本番はサンプリング、正確な回数・レアイベントが必要な局面だけ期間と対象を絞ってトレーシング
- [ ] **単一マシン内並列化 vs 複数マシンへの分散（scatter/gather）** (perf-t-007): まず単一マシンの並列化で足りるか検討し、コア数・帯域の限界で分散に切り替える
- [ ] **内部ステートストア vs 外部ステートストア** (perf-t-008): 遅延・スループット・コスト・スケーリング・データアクセスパターンの5要素で明示的に比較する
- [ ] **PEFT（アダプター等）vs フル・ファインチューニング** (perf-t-009): 多数タスク向けはPEFTでメモリ削減し、推論レイテンシ増（6〜8%程度）と系列長減をSLOと突き合わせる
- [ ] **GPU vs CPU：バッチスループット vs レイテンシ vs コスト** (perf-t-010): GPUはバッチ処理向き。CPUベースラインとの差分とデータ転送コスト込みで判断する
- [ ] **メモリセーフ言語 vs 低レベル制御** (perf-t-011): 原則メモリセーフ言語を選び、メモリレイアウト制御が本当に必要な部分だけ低レベル言語にする
