# Code-Review Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/code-review/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。
> 2026-10-02: active カードのみ掲載（F2 昇格 32 枚）。candidate は精査パケット output/kb-promotion/2026-10-code-review.md を参照。

## ベストプラクティス（適用を検討したか）

- [ ] **レビューコメントはTODOとして扱い、不同意なら理由と代案を示してから解決済みにする** (cr-p-001): レビュアーの各コメントをTODO項目として扱い、少なくとも全コメントに対処する（無条件に受け入れる必要はない）
- [ ] **レビュアーは作者のアプローチを断定で否定せず、理由を質問してから代案を示す** (cr-p-002): 作者のアプローチが不十分な場合にのみ代案を指摘する
- [ ] **レビューのフィードバックは速く、まとめて返す** (cr-p-003): レビューのフィードバックは迅速に返す。Googleでは24（勤務）時間以内に行うことが期待されている
- [ ] **コードレビューで、作者以外の目で理解可能性を検証し、理解の質問を妥当なものとして扱う** (cr-p-005): レビューを、変更が広い読み手にとって理解可能かを確かめる最初の機会として使う
- [ ] **変更は約200行までの単一課題に絞り、大きすぎる変更は分割を求める** (cr-p-007): 1つの変更は噛み砕いて理解しやすく、ただ1つの問題に集中したものにする
- [ ] **スタイル・規約の指摘にはその根拠を添え、合否判定でなくメンタリングとして行う** (cr-p-009): レビューコメントには、関連する典拠（スタイルガイドなどの文書）を添える
- [ ] **状態を変える関数と問い合わせる関数を分け、if条件に副作用のある呼び出しを置かない** (cr-p-010): コマンド（状態を変える）とクエリ（問い合わせる）を別の関数に分ける（例: attributeExists で確認してから setAttribute を呼ぶ）
- [ ] **エラーコードを返さず例外を使い、try/catchの中身は専用の関数に切り出す** (cr-p-011): 可能な限りエラーコードより例外を優先する。コマンド関数のエラーコード返却はコマンド/クエリ分離の微妙な違反でもある
- [ ] **関数名は実装を隠した動詞で付け、文脈が詳細なら長くしてよい** (cr-p-013): 名前は動詞・動詞句・暗黙の動詞（Math.sign(x) のような形）にし、コードより少しだけ抽象的な記述にして実装を隠す（addAtoBandDivideBy2 でなく average）
- [ ] **コミットとPRを「1つの小さな課題」の単位にし、1文で説明できなければ分割する** (cr-p-014): コミットは、1つの小さく比較的自己完結した作業だけを行い、その作業を短い1文で言える形にする。その1文がコミットメッセージの要約になる
- [ ] **自分のコードを他者にレビューしてもらう仕組みを決め、全変更をその経路に通す** (cr-p-015): 作者以外の人によるレビューを必須にする。本書はこれがバグ検出に有効で、欠陥率を50〜80%下げ得るとしている
- [ ] **レビューのガイドラインを先に定め、機械化できる指摘（書式など）を人のレビューから外す** (cr-p-016): 採用するレビュー方式にかかわらず、レビューのガイドラインを事前に定義し、チーム全体で一貫して繰り返せるプロセスにする
- [ ] **コミットメッセージには「何を変えたか」と「なぜ変えたか」を書く** (cr-p-019): メッセージで、何が変わったか（what）と、なぜ変えたか（why）の両方を説明する
- [ ] **レビューの労力は機械で検出できない観点に使う（命名・可読性・重複・ログ・インタフェース・抽象化）** (cr-p-021): 書式とスタイルに関する指摘は自動化し、レビュアーの時間は機械が検出できないものに使う
- [ ] **誤りやすい書き方（括弧を省略した単文のif）を避け、規約と静的解析で防ぐ** (cr-p-022): 誤りやすい形をツールチェーンで避ける。例: Javaで単一文のifの括弧を省略した形では、後から2つ目の文を足したとき、インデントに惑わされて括弧を忘れる
- [ ] **テキストでは伝わらない口調に配慮し、懸念は事前に1対1で話し、皮肉を避ける** (cr-p-023): 皮肉や当てこすりを使わない。レビューの目的はコードを改善することであり、技術的知識の誇示ではない
- [ ] **レビューコメントに理由と重要度（必須か、推奨か、好みか）を明記する** (cr-p-024): 何がダメかだけでなく、なぜダメかも説明する。短い説明や、特定の記事・Stack Overflow投稿へのリンクを添える
- [ ] **レビューの段階と文脈に合わせて指摘の粒度を変え、概要から詳細へ進める** (cr-p-025): まず、課題を理解するコンテキストを確認する（言語に不慣れで学びたいのか、安全のための第三者の視点がほしいだけなのか）
- [ ] **異論が無ければ「LGTM」と明示し、作業が多いPRはコメントで埋めず話すかペアで進める** (cr-p-026): 自分のコメントが対応を求めるものか、満足しているかを明確に伝える
- [ ] **ビルド直後に静的解析を走らせ、バグ・脆弱性・コード臭・規約違反を人のレビュー前に洗い出す** (cr-p-027): コードをビルドした直後に、静的解析ツールを実行する
- [ ] **テストコードも読みやすく保ち、無関係な詳細を隠してArrange/Act/Assertを明確にする** (cr-p-029): テストの可読性は、本番コード以上に重要になり得るとして扱い、明快さ・単純さ・表現の密度を求める
- [ ] **設計の優先順位は、テスト、表現、重複排除、サイズ縮小の順にし、重複排除を先走らない** (cr-p-030): まずテスト（カバレッジ）を整え、次にコードが意図を表現するようにし、その後で重複を排除する

## アンチパターン（該当していないか）

- [ ] **同じ型による分岐（switch / if-else）を複数の関数にばらまく** (cr-a-002): レビューで、同じ種別（例: movieType）に対する switch や if/else の連鎖が複数の関数（determineAmount、determinePoints など）に現れていないか確認する
- [ ] **PRを開いた時点で動くパイプラインに書き込み権限を与え、レビューと承認を迂回させる** (cr-a-003): PRを開いたときに実行するplan工程には読み取り権限だけ、マージ後に実行するapply工程には読み取りと書き込みの両方を与える（権限を分ける）
- [ ] **チェックボックスのためだけのレビュー（「LFTM」だけで承認する）を行う** (cr-a-004): レビューの承認が、実質的な確認なしの「LFTM（looks fine to me）」だけになっていないかを確認する
- [ ] **変更を最も理解している人でなく外部の承認者が承認する、形だけのレビュー（CAB型）** (cr-a-006): 承認の意思決定は、変更について最も深く理解している人が行う形になっているかを確認する
- [ ] **偶然の重複（意図が異なる似たコード）を共通化して結合してしまう** (cr-a-007): 重複を見つけたら、本物の重複か偶然の重複かを、意図で区別する。偶然の重複は意図が分岐しており、本物の重複は意図が収束している
- [ ] **緊急パッチやデッドコードをコードベースに残し続ける** (cr-a-009): 応急の雑なパッチを入れた場合は、本番の危機を収める目的に限って許容し、その後コードベースに残さず整理する

## トレードオフ（明示的に判断したか）

- [ ] **スタイルガイドのルールを増やす vs 全員が覚える・保守するコスト** (cr-t-004): 新しいルールを足す前に、全エンジニアに学ばせ適用させるコストがゼロではないことを織り込む
- [ ] **重複コードを関数に切り出す vs 重複のまま残す（重複の長さと箇所数で判断）** (cr-t-006): 重複の長さL（行数）と重複の箇所数Pの両方を見る。LもPも小さければ、重複の害は小さく、排除の労力のほうが害になり得る
- [ ] **関数の抽出を進める vs 抽出した関数間で共有する状態の危険（スコープ変数と並行性）** (cr-t-007): 抽出して命名し直すだけで読みやすさが上がるかを確認する。大きく複雑になるモジュールほど効果が大きい
- [ ] **マージ前にrebaseして最新mainに合わせる vs 共有ブランチの履歴を書き換えるリスク** (cr-t-009): 作業は専用の機能ブランチで行い、統合できる状態になるまでmainを安定に保つ
