## ベストプラクティス（適用を検討したか）

- [ ] **ストラングラーパターンによる段階的モノリス置換** (arch-p-001): まずモノリスの前段にプロキシ/ファサードを置き、外部からの呼び出し経路を制御下に置く
- [ ] **分散システムはシステムモデルの仮定を明示して設計する** (arch-p-007): 設計の最初に、ネットワーク・クロック・プロセス停止についてどんな前提（システムモデル）を置くかを文書化する
- [ ] **モノリス分解は先に「道を舗装」してから小さく始める** (arch-p-009): 分解に着手する前に、コンテナ化・オーケストレーション・ログ集約・モニタリング・分散トレーシングなどランタイム基盤を先に整備する
- [ ] **「AよりもBを優先する」宣言でトレードオフを明文化する** (arch-p-010): 設計ドキュメントやADRに、望む成果の2つの正の属性を対にして「XよりもYを優先する」形式で書く（例：性能よりも使いやすさ、市場投入速度よりも長期保守性）
- [ ] **部分障害を前提とした分散システム設計と冪等リトライ** (arch-p-012): ネットワークと複数ノードが絡む処理は「時々失敗する」「成功したか不明なことがある」を設計の前提に置く
- [ ] **ゼロトラスト適用はリソース分離アーキテクチャが前提** (arch-p-014): ゼロトラスト移行の前に、アーキテクチャがそれを支えられるかを評価する。API・ビジネスロジック・DBが1つのコンテナに同居していると、リソース単位の細粒度権限は実質付与できない
- [ ] **設計・コード・変更レビューの体系的チェック観点** (arch-p-017): レビュー対象を3種類に分ける: コード、設計、そして「変更」（実施予定の操作手順そのもの）。本番操作は実行前に手順を書き出し、第三者の合意を得る

## アンチパターン（該当していないか）

- [ ] **DB更新とメッセージ発行の二重書き込み** (arch-a-006): 「DB書き込み→バス発行」を素朴に並べたコードをレビューで見つけたら、中間障害時の整合性を必ず問う

## トレードオフ（明示的に判断したか）

- [ ] **モノリス採用の判断基準：単一デプロイの利点と代償** (arch-t-001): 「モノリス=大きな泥団子」ではなく「単一デプロイ単位」と正しく定義して比較する（内部がモジュール化されたモノリスは正当な選択肢）
- [ ] **垂直スケール vs 水平スケールの選択** (arch-t-002): まず垂直スケール（単一マシンの資源増強）で足りるかを検証する。実装が単純で分散の複雑さを持ち込まない
- [ ] **API方式はデータの複雑さと呼び出し側コストで選ぶ** (arch-t-004): データ構造が単純でリレーションの横断取得が不要なら、最も単純なREST（HTTP+JSON）を既定にする
- [ ] **ドキュメントDB採用：スキーマ/ACID緩和と引き換えの読み書き性能** (arch-t-005): ドキュメントDBの性能優位の源泉を理解して選ぶ：多ノードへの負荷分散と、スキーマ検査・制約・ACID特性の強制を緩めた設計
- [ ] **性能改善の余地を潰す初期決定を避ける** (arch-t-007): 「後で直せる性能問題」と「初期決定で固定される性能上限」を区別し、後者（ストレージ構成・言語・基盤選定）は初期に検討する
- [ ] **NoSQLストアはワークロードのアクセスパターンで選ぶ** (arch-t-009): キーバリューストア：キー直アクセスの低レイテンシ読み書き（キャッシュ、セッション管理、リアルタイム処理）に使う。複雑なクエリや複数キーにまたがるトランザクションは弱く、複雑な関係はアプリ層で処理する負担が生じる
- [ ] **LLMリフレクションの深さはコストと品質で調整する** (arch-t-010): ラウンド数や評価しきい値を上げる前に、品質改善の見込みと追加コスト・遅延を用途ごとに見積もる
- [ ] **初期の泥団子アーキテクチャの許容とクラウド移行戦略の選択** (arch-t-012): ドメイン理解が浅い初期は、まず動くものを作ってフィードバックを得る方針を許容する。動作優先→構造化→性能最適化の順で段階的に品質を上げる
- [ ] **リードレプリカ追加による読み取りスケールの限界** (arch-t-013): 単一リーダー構成では書き込みはリーダー、読み取りはフォロワーに分離するのが基本形。読み取り偏重ならレプリカ追加は有効な第一手
- [ ] **ドキュメントストア採用の判断基準** (arch-t-015): 向く条件: スキーマの動的進化、柔軟なデータモデリング、非構造化/半構造化データ（ユーザー生成コンテンツ、ログ、センサーデータ等）の格納・検索が主要件
- [ ] **shared-nothing構成によるスケーラビリティ確保** (arch-t-016): ノードを追加しても外部の共有リソース（共有ディスク、共有ネットワークスタック等）への競合が増えない構成にすると、線形に近いスケールが可能になる
