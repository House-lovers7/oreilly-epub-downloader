# Architecture Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/architecture/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **ストラングラーパターンによる段階的モノリス置換** (arch-p-001): まずモノリスの前段にプロキシ/ファサードを置き、外部からの呼び出し経路を制御下に置く
- [ ] **抽出の前にリファクタリング：モジュラーモノリス経由で分割する** (arch-p-002): いきなりサービス抽出せず、まずモノリス内部で明確なインタフェースを持つモジュールへ再編する
- [ ] **移行判断の前にモジュール性を計測する** (arch-p-003): 移行計画を立てる前に、アーキテクチャ評価手法で品質・信頼性要件を明文化する
- [ ] **障害前提設計：冗長化とクォーラムで可用性を作る** (arch-p-004): 「十分な時間が経てば必ずどこかが壊れる」を設計の前提に置き、単一マシン構成を可用性要件と突き合わせて棄却判断する
- [ ] **共同モデリングでサービス境界を発見する** (arch-p-005): 境界設計の入力として、EventStormingやドメインストーリーテリング等の共同モデリング手法でドメインイベントを洗い出す
- [ ] **大規模移行は低リスク領域から順序付ける（Netflix型の段階戦略）** (arch-p-006): 顧客に直接影響しないワークロード（バッチ、ログ基盤等）から移行を始め、学習と検証をリスクの低い場所で行う
- [ ] **分散システムはシステムモデルの仮定を明示して設計する** (arch-p-007): 設計の最初に、ネットワーク・クロック・プロセス停止についてどんな前提（システムモデル）を置くかを文書化する
- [ ] **望ましい状態を宣言しオーケストレータに調整を任せる** (arch-p-008): デプロイ構成は「レプリカ数などの望ましい状態」を宣言的に記述し、実状態との一致はKubernetes等のオーケストレータに担わせる
- [ ] **モノリス分解は先に「道を舗装」してから小さく始める** (arch-p-009): 分解に着手する前に、コンテナ化・オーケストレーション・ログ集約・モニタリング・分散トレーシングなどランタイム基盤を先に整備する
- [ ] **「AよりもBを優先する」宣言でトレードオフを明文化する** (arch-p-010): 設計ドキュメントやADRに、望む成果の2つの正の属性を対にして「XよりもYを優先する」形式で書く（例：性能よりも使いやすさ、市場投入速度よりも長期保守性）
- [ ] **レイヤ分割で書き込み側と読み取り側の最適化を分離する** (arch-p-011): 取り込み層（ブロンズ）は生成側の制約に合わせて書き込み効率を最適化し、提供層（ゴールド）は利用者のクエリ向けに最適化する、というメダリオン型の関心分離を使う
- [ ] **部分障害を前提とした分散システム設計と冪等リトライ** (arch-p-012): ネットワークと複数ノードが絡む処理は「時々失敗する」「成功したか不明なことがある」を設計の前提に置く
- [ ] **長時間タスクは同期APIでなく分散オーケストレーションで扱う** (arch-p-013): サービス間通信はAPIかイベントを基本とし、ハードな直接依存を避ける
- [ ] **ゼロトラスト適用はリソース分離アーキテクチャが前提** (arch-p-014): ゼロトラスト移行の前に、アーキテクチャがそれを支えられるかを評価する。API・ビジネスロジック・DBが1つのコンテナに同居していると、リソース単位の細粒度権限は実質付与できない
- [ ] **ID型やキャパシティの不安は算術見積もりで解消する** (arch-p-015): 不安を感じたら設計変更の前に計算する: 単位時間あたりの消費量（例: 毎分の挿入行数）を見積もり、型の最大値を割って枯渇までの期間を出す
- [ ] **変更容易性を軸にした設計判断（分割と依存の2軸）** (arch-p-016): 良い設計の中心基準を「安全かつ容易に変更できること」に置く。理解しやすさ、問題修正のしやすさ、新要件への適応しやすさはすべてここに従属する
- [ ] **設計・コード・変更レビューの体系的チェック観点** (arch-p-017): レビュー対象を3種類に分ける: コード、設計、そして「変更」（実施予定の操作手順そのもの）。本番操作は実行前に手順を書き出し、第三者の合意を得る

## アンチパターン（該当していないか）

- [ ] **早すぎる分散化：独立性のないマイクロサービス分割** (arch-a-001): 分割の目的を「複数開発者/チームが調整最小で独立作業できること」に置き、その必要が生じてから分割する
- [ ] **YAGNIの誤用：利用者の実行環境を無視した性能設計の先送り** (arch-a-002): YAGNIで省いてよいのは投機的な機能であり、想定ユーザーの実行環境制約（メモリ上限、マシンサイズ）は初期設計の入力として扱う
- [ ] **外部キー制約の省略** (arch-a-003): 外部キー制約を外す判断は「整合性保証コードをアプリ側で書き続ける負債」との交換であると明示してレビューする
- [ ] **ポリモーフィック関連（二重目的の外部キー）** (arch-a-004): 1列で複数テーブルを指す設計は、DBの外部キー制約で整合性を宣言できなくなるため避ける
- [ ] **密結合モノリスの放置と分散モノリス化** (arch-a-005): モノリスを評価する際は技術的結合とドメイン結合を別々に測り、どちらが問題かを特定する
- [ ] **DB更新とメッセージ発行の二重書き込み** (arch-a-006): 「DB書き込み→バス発行」を素朴に並べたコードをレビューで見つけたら、中間障害時の整合性を必ず問う
- [ ] **全テーブルへの機械的なid列の付与** (arch-a-007): テーブルごとに、自然キーや複合キーが主キーとして適切でないかをまず検討する
- [ ] **カンマ区切りリストを1列に格納する** (arch-a-008): 1つの属性に複数の値を持たせたくなったら、交差テーブル（関連テーブル）を作って1行1値で表現する
- [ ] **データ増加のたびにテーブルや列をコピーして増やす** (arch-a-009): データ量の増加にはスキーマ増殖ではなく、パーティショニングやインデックス設計などDB側の機構で対応する
- [ ] **キャッシュ前提の容量設計（キャッシュの暗黙ハード依存）** (arch-a-010): キャッシュ追加時に「キャッシュ全損時にオリジンDBが読み取り負荷を捌けるか」を必ず設計レビューで問う
- [ ] **暗黙の分散トランザクションの見落とし** (arch-a-011): 「DB更新の成否」と「呼び出し元への通知」が別システム間の状態伝搬であることを認識し、失敗パターン（更新成功+応答喪失、更新失敗+呼び出し元は成功と誤認）を列挙する
- [ ] **多値属性を連番カラムで持つ（マルチカラム属性）** (arch-a-012): 多値属性は連番カラムではなく、従属テーブル（交差テーブル）に行として正規化して持つ

## トレードオフ（明示的に判断したか）

- [ ] **モノリス採用の判断基準：単一デプロイの利点と代償** (arch-t-001): 「モノリス=大きな泥団子」ではなく「単一デプロイ単位」と正しく定義して比較する（内部がモジュール化されたモノリスは正当な選択肢）
- [ ] **垂直スケール vs 水平スケールの選択** (arch-t-002): まず垂直スケール（単一マシンの資源増強）で足りるかを検証する。実装が単純で分散の複雑さを持ち込まない
- [ ] **密結合と疎結合はスペクトラム：疎結合にはガバナンスを添える** (arch-t-003): 結合度を二値でなくスペクトラムとして捉え、ドメインごとに位置を選ぶ
- [ ] **API方式はデータの複雑さと呼び出し側コストで選ぶ** (arch-t-004): データ構造が単純でリレーションの横断取得が不要なら、最も単純なREST（HTTP+JSON）を既定にする
- [ ] **ドキュメントDB採用：スキーマ/ACID緩和と引き換えの読み書き性能** (arch-t-005): ドキュメントDBの性能優位の源泉を理解して選ぶ：多ノードへの負荷分散と、スキーマ検査・制約・ACID特性の強制を緩めた設計
- [ ] **Sagaの調整方式：コレオグラフィかオーケストレーションか** (arch-t-006): コレオグラフィ：各サービスがイベントを介して直接連携する。中央の単一障害点がない一方、各サービスが業務プロセス全体・連携相手・交換メッセージを知る必要がある
- [ ] **性能改善の余地を潰す初期決定を避ける** (arch-t-007): 「後で直せる性能問題」と「初期決定で固定される性能上限」を区別し、後者（ストレージ構成・言語・基盤選定）は初期に検討する
- [ ] **技術選定における使いやすさ対パフォーマンス** (arch-t-008): 選定時に「複雑さ」を具体化する：学習曲線、コード内で管理すべき要素数、セットアップ・デバッグ・他環境再現・統合・拡張・デプロイの難度
- [ ] **NoSQLストアはワークロードのアクセスパターンで選ぶ** (arch-t-009): キーバリューストア：キー直アクセスの低レイテンシ読み書き（キャッシュ、セッション管理、リアルタイム処理）に使う。複雑なクエリや複数キーにまたがるトランザクションは弱く、複雑な関係はアプリ層で処理する負担が生じる
- [ ] **LLMリフレクションの深さはコストと品質で調整する** (arch-t-010): ラウンド数や評価しきい値を上げる前に、品質改善の見込みと追加コスト・遅延を用途ごとに見積もる
- [ ] **モノリスから分散アーキテクチャへ移行する判断基準** (arch-t-011): 「独立してデプロイしたい単位」が複数チームに分かれて存在するかをまず確認する。存在しないなら分散化の便益は薄い
- [ ] **初期の泥団子アーキテクチャの許容とクラウド移行戦略の選択** (arch-t-012): ドメイン理解が浅い初期は、まず動くものを作ってフィードバックを得る方針を許容する。動作優先→構造化→性能最適化の順で段階的に品質を上げる
- [ ] **リードレプリカ追加による読み取りスケールの限界** (arch-t-013): 単一リーダー構成では書き込みはリーダー、読み取りはフォロワーに分離するのが基本形。読み取り偏重ならレプリカ追加は有効な第一手
- [ ] **メッセージキュー導入の便益と複雑性** (arch-t-014): 得られるもの: 水平スケール、動的なスケールアップ/ダウン、下流遅延時のバッファリング、メッセージ永続化による障害耐性
- [ ] **ドキュメントストア採用の判断基準** (arch-t-015): 向く条件: スキーマの動的進化、柔軟なデータモデリング、非構造化/半構造化データ（ユーザー生成コンテンツ、ログ、センサーデータ等）の格納・検索が主要件
- [ ] **shared-nothing構成によるスケーラビリティ確保** (arch-t-016): ノードを追加しても外部の共有リソース（共有ディスク、共有ネットワークスタック等）への競合が増えない構成にすると、線形に近いスケールが可能になる
- [ ] **AIエージェントフレームワーク選定（制御性 vs 立ち上げ速度）** (arch-t-017): 制御性重視ならグラフ型: ロジック単位をノード、データフローをエッジで明示するため、循環を含む複雑なワークフローでもフローが検査可能・デバッグ可能になる。堅牢性の高い単一エージェントや軽量マルチエージェントに向く
