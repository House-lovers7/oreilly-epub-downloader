# Sre Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/sre/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。
> 2026-10-02: active カードのみ掲載（F1-2 昇格 15 枚＋R1 昇格 3 枚）。candidate は精査パケット output/kb-promotion/2026-10-sre.md を参照。

## ベストプラクティス（適用を検討したか）

- [ ] **SLA→SLO→SLIの逆算設計** (sre-p-001): まずユーザー・顧客への約束（SLA相当）をユーザーに見える言葉で1つ定義する（例: データが毎朝X時までに利用可能な日が99%以上）
- [ ] **計装はOpenTelemetry等のオープン標準で行う** (sre-p-005): 新規サービスの計装はOpenTelemetryを既定とし、トレース・メトリクス・ログをベンダー中立に生成する
- [ ] **デプロイとリリースを別フェーズに分離する** (sre-p-006): デプロイ=環境への変更配信、リリース=ユーザーへの機能公開、と定義を分けてパイプラインを設計する
- [ ] **ビルド・リリース・実行を分離し不変アーティファクトを使う** (sre-p-008): ビルド段階で一意なID（ビルド番号等）付きの実行可能アーティファクトを自動生成する
- [ ] **リクエストコンテキスト（トレースID・テナントID）を全ホップで伝搬する** (sre-p-009): リクエストの発生源にできるだけ近い場所で一意な相関ID/トレースヘッダを付与し、以後の全サービス呼び出しに伝搬させる
- [ ] **ユーザーフィードバックを可観測性シグナルとして統合する** (sre-p-011): 暗黙のフィードバック（タスク放棄率、再クエリ頻度、入力の言い換え）をメトリクスとして収集し、既存の監視スタックで可視化する
- [ ] **インシデント対応は止血優先と能動的検知で行う** (sre-p-012): 障害発生時はまず影響の遮断を最優先し、根本修正は後回しにする（機能の一時停止・精度を落とした縮退運転・正常なインスタンスへのトラフィック切り替えなど）
- [ ] **SLI/SLOは合意形成し期待値として公開する** (sre-p-013): SLIはサービスの1側面を表す計測可能な指標を、意味を理解した上で少数厳選する（例: リクエスト成功率、レスポンスタイム）
- [ ] **複数ウィンドウ×複数バーンレートのSLOアラート** (sre-p-014): バーンレート（エラーバジェット消費速度）を軸に、長期ウィンドウと短期ウィンドウのAND条件でアラートを組む
- [ ] **エラーバジェットでリリース速度と安定化を調停する** (sre-p-015): SLOから許容可能な違反量（エラーバジェット）を導出する。例: 週次99.9%なら週あたり約10分の違反が許容枠
- [ ] **デプロイ手順と戦略を全環境で一貫させる** (sre-p-017): 本番で使うデプロイ戦略（カナリア、ブルーグリーン、フィーチャーフラグ）は本番前環境でも同じ方式で再現する
- [ ] **運用責任の開発チーム移譲は支援体制とセットで行う** (sre-p-018): 「作った者が運用する」への移行は、権限だけでなく知識とツールをセットで引き渡す
- [ ] **クラウドネイティブでは高カーディナリティなイベントで観測する** (sre-p-020): 各イベントに多数のキーと値のペア（高ディメンション・高カーディナリティ）でコンテキストを付与し、後から任意の切り口で相関分析できるようにする

## アンチパターン（該当していないか）

- [ ] **ツール導入だけでオブザーバビリティが得られると考える** (sre-a-002): ツール選定と同時に、仮説駆動・反復型のデバッグ手法（コア分析ループ等）をチームの標準手順として整備する
- [ ] **短時間ウィンドウの生エラー率だけでアラートする** (sre-a-004): アラート設計は適合率（precision）・再現率（recall）・検出時間・リセット時間の4軸で評価する
- [ ] **サーバーレスでの無秩序なログ大量出力** (sre-a-005): ログの過剰出力はデバッグに要する時間と知識を逆に増やす。ログは設計対象として絞る

## トレードオフ（明示的に判断したか）

- [ ] **SLO評価ウィンドウ：ローリング vs カレンダー** (sre-t-004): ユーザー体験への忠実さを重視するならローリングウィンドウを選ぶ（月末の障害を翌月初に忘れない）
- [ ] **クラウド時代のキャパシティプランニング：精密計画か動的サイジングか** (sre-t-006): クラウドではインスタンスの追加・削除が即時かつ安価なため、詳細な事前計画より「モニタリング指標に基づく動的サイジング（オートスケール）」を基本にできる
