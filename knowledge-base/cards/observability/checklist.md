## ベストプラクティス（適用を検討したか）

- [ ] **ログ出力行ごとに機密情報の混入を確認する** (obs-p-001): ログ出力を追加する各行について、パスワード・APIキー・ユーザーを特定できる情報（メール、アカウントID）が含まれ得ないかを確認する
- [ ] **ログレベルは読み手と対応要否を基準に使い分ける** (obs-p-002): 開発中の詳細は DEBUG、通常の状態は INFO、想定外で人間の介入が必要になり得る事象は ERROR に割り当てる
- [ ] **アラートは対応の緊急度で分類し、依存先の障害と重複する通知は抑制する** (obs-p-004): アラートをカテゴリ・重要度で分類し、100%エラー率のような緊急事態は即時対応、1時間以上続く低率エラーはチケット起票に振り分ける
- [ ] **ページには関連コンソールとプレイブックを紐づけ、変更履歴を検索可能にしておく** (obs-p-005): ページが関連するモニタリングコンソールにリンクされ、仕様外の動作をしている部分がハイライトされるようにする
- [ ] **ログは作業単位でスコープを切った1イベントにし、分ける場合は共通IDを入れる** (obs-p-006): HTTPリクエストの処理など、サービスにとっての作業単位を1つ決め、その実行に必要な入力・途中で解決/発見した属性・実行時のサービス状況・結果の詳細を1つの構造化イベントに集約する
- [ ] **レイテンシは平均でなく分布で集計し、元になる生データを残す** (obs-p-007): レイテンシの集計に平均・中央値・標準偏差だけを使わず、分布を把握できる90・95・99・99.9パーセンタイルやヒストグラムを併用する
- [ ] **レイテンシ指標は実用上意味のある下限と上限の範囲で定義する** (obs-p-008): ユーザー端末起点のレイテンシで、チューニングを打ち切る判断に使う下限として、「0ミリ秒以上100ミリ秒以下」ではなく「25ミリ秒から100ミリ秒」のように、ユーザー環境から見て意味のある下限と上限で書く
- [ ] **アラートの文面は何が起き、何を調べ、どう反応するかが分かる具体的なものにする** (obs-p-010): アラートには、何が起きたか・何を調査すべきか・どう反応すべきかを読み取れる固有の名前と内容をつける
- [ ] **分散トレースのレコードに要求ID・階層位置・時刻・エラー状態を持たせる** (obs-p-011): 各サービス要求のログに、アプリケーション要求を一意に識別するID(外部要求ID)を書く
- [ ] **「エラーが無い」ではなく処理が流れていることを示すメトリクスを置く** (obs-p-012): 注文処理など主要な業務処理ごとに、エラーが無いことの確認にとどめず、処理が完了している件数を示す指標を置く
- [ ] **アラートの宛先は所有権と文脈を持つ1人に絞る** (obs-p-013): 通知の宛先は、対象に高い所有権を持ち、トリアージとルーティングのインセンティブがある人にする
- [ ] **ログ・アラート基盤自体の健全性を定期的に検証し、ログ量の異常も監視する** (obs-p-014): すべてのログを一元的に収集し、異常なアクセスや活動がないか一貫して監視する
- [ ] **ログ調査は時刻とユニットで絞り、一致行の前後も確認する** (obs-p-015): まず時間範囲(例: 過去4時間、特定の日時以降)で絞り込む
- [ ] **サービス廃止時は監視・アラート・データ収集も一緒に撤去する** (obs-p-016): サービスを廃止するときは、すべての依存関係を洗い出す。サードパーティとの統合も同様
- [ ] **異常値を見たら、実事象かデータ収集・処理の誤りかを先に切り分ける** (obs-p-017): 異常の原因を、極端な実際の事象か、データの収集・処理中に生じたエラーかに分けて確認する
- [ ] **自動化の実行前チェックに、人間向けと同じモニタリング・アラートのデータを使う** (obs-p-020): 自動化のすべてのアクションは、実行前に安全性を評価する。処理能力や冗長性を削る変更も含める

## アンチパターン（該当していないか）

- [ ] **閾値超過をメールで送り人間が毎回解釈する運用** (obs-a-001): アラートの判定はソフトウェア側で行い、人間は対応が必要なときだけ通知を受ける設計にする
- [ ] **最古参の勘や過去の障害の記憶でグラフを選び、確認だけして原因とみなす** (obs-a-003): 原因調査では、システム情報の痕跡を手がかりにデータから探索的に絞り込み、推測の確認にとどめない
- [ ] **tail -f での目視を継続的な監視の代わりにする** (obs-a-004): ログの tail/follow は、問題を調べているときや、起動・運用をリアルタイムで詳しく見たいときの調査手段として使う
- [ ] **個々の外れ値の検出をそのままデータ品質アラートにする** (obs-a-005): アラートの対象は、到着するデータの分布に突然の構造的変化(分布・パターン・関係の大きな変化)が起きたことにする
- [ ] **障害モードごとにダッシュボードを足し続ける運用を複雑化したシステムでも続ける** (obs-a-006): 従来のモニタリングが暗黙に置いている前提(モノリス、データストアは1つ、ホストの集合が静的、調べるのは問題発生後、相関の調査は少数のディメンションで足りる、など)が自システムで成り立つか点検する
- [ ] **カスタムメトリクスを見境なく増やしてコストが線形に膨らむ** (obs-a-007): カスタムメトリクスを追加するレビューで、1つ増えるごとに費用が線形に増える料金体系かどうかを確認する。熱心に増やすと請求を見て驚き、その大部分を削除する事態になる
- [ ] **ホストへのsshで調べる前提のデバッグ手段に頼る** (obs-a-008): 事象ごとに多くのキー・値のペアの形でコンテキストを付けて記録し、システム内部の状態を事後に調べられるようにする

## トレードオフ（明示的に判断したか）

- [ ] **既存のモニタリングを維持するか、オブザーバビリティへ置き換えるか** (obs-t-001): 安定したサービスを提供できているメトリクスベースのモニタリング・ダッシュボード・非構造化ログ検索は、置き換えの価値があまり無ければそのまま使い続ける
- [ ] **トレースのサンプリング:ヘッドベース vs テールベース** (obs-t-002): 大多数の要求のパフォーマンス分析で足りるなら、要求の最初の時点でトレースするか決めるヘッドベースサンプリング(例: 1万要求に1個)を使う
- [ ] **データ品質監視: 手作りルール・メトリクス vs 教師なしML** (obs-t-003): 手作りの規則やメトリックは、重要なデータやリレーションシップに絞って使う。全データに広げるとセットアップと保守に時間がかかり、アラートがノイズだらけになる
- [ ] **外れ値の扱い:代替値に置き換えるか、要約するか** (obs-t-004): 正しい値が分かっている誤り(桁違い、単位違いなど)は、条件式で置き換え、データセットの行数を維持する
- [ ] **ロギング・トレースの共通抽象化を提供するか、各チームの個別実装に任せるか** (obs-t-005): ロギング、可観測性、トレースなどは、共通の抽象化と各チームが従う共通パターンを提供する。提供しない限り、全チームが一貫した方法で個別実装することはできず、無駄にもなる
- [ ] **ログ基盤の選択(systemd系Linuxホスト限定):syslog系(集約・多出力) vs journald(単一マシンで統一形式)** (obs-t-006): 複数のマシンのログを集約して監視したい、あるいは多様な形式やデータベースへ出力して分析・監視ツールにつなぎたいなら、syslog系(rsyslogなど、モジュール式)を選ぶ
- [ ] **データウェアハウスのデータ品質監視: ML監視の範囲 全体 vs 重要なデータに絞る** (obs-t-007): アラートの量を減らしたいなら、MLで監視する対象を、本当に重要なテーブルだけに絞る
