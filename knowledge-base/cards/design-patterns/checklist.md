## ベストプラクティス（適用を検討したか）

- [ ] **ストリーミングデータ処理パターンの選択基準** (dp-p-001): イベントの形式・構造・プロトコル変換にはトランスフォーメーションパターンを使う。サードパーティシステムが現イベントに未対応の場合に有効。
- [ ] **デザインパターン導入前に価値を問う（過剰設計の回避）** (dp-p-002): 採用しようとしているパターンが実装に『本当の価値』を提供できるかどうかを検討してから採用する。
- [ ] **Goのpluginパターン：Openの挙動と再ロード制約** (dp-p-003): plugin.Open(module)でプラグインをメモリにロードし、返された*Plugin値からエクスポートされたシンボルを参照する。
- [ ] **境界づけられたコンテキストは機能ドメイン単位でグルーピングして結合を下げ凝集度を上げる** (dp-p-004): 結合（コンテキスト間の相互依存）を下げる：コンテキスト間でビジネスロジックや内部プロセスの知識を共有しないよう設計する
- [ ] **ドメイン知識によるソースコード強化は技術的安定化の後に着手する** (dp-p-005): システムの技術的な安定性を確保してから、戦術的なドメイン駆動型変換（ドメイン知識によるソースコード強化）に移行する
- [ ] **安全なメソッドリネーム：転送メソッドによる段階的移行** (dp-p-006): 新しい名前で新しいメソッドを追加する（旧メソッドと同じシグネチャ）。新メソッドは旧メソッドへの単純な転送として実装する。
- [ ] **モノリス→マイクロサービス移行：Proxy+Facadeによる橋渡しとプレイバックテスト検証** (dp-p-007): 対象機能をReplace as Microserviceでマイクロサービスとして書き換え、完成後は他チームに周知する。
- [ ] **モジュール設計：高凝集・疎結合を目指しつつ結合の種類でバランスを取る** (dp-p-008): モジュール分割時は、内部の構成要素が概念的・機能的に密接に関連する（凝集度が高い）まとまりを作る。

## トレードオフ（判断を明文化したか）

- [ ] **ストリーム処理フレームワークの選定（Flink/Esper/Azure Stream Analytics）** (dp-t-001): マイクロサービスやサーバーレス関数にストリーム処理ロジックを実装する際、どのフレームワークを選ぶべきか。
- [ ] **D.I.E.（分散・不変性・エフェメラル）パターンへの疎結合投資は対象を選ぶ** (dp-t-002): 疎結合への投資（攻撃者が辿れる攻撃パスを減らす設計）はどのコンポーネントにも同じ効果があるわけではなく、投じられる労力資本には限りがある。どこに投資すべきかの判
- [ ] **Basic RAG（索引化・検索・生成の3ステップ）はそのまま本番採用せず出発点として扱う** (dp-t-003): RAGシステムをどこから設計し始めるべきか、また最小構成の3ステップ実装をそのまま本番要件に採用してよいかの判断が必要。
- [ ] **モノリス分割の粒度：クリーンな小分割が難しい場合はマクロサービスから始める** (dp-t-004): モノリスの機能が絡み合っていて小さな単位でのマイクロサービス切り出し・書き換えができない場合、どの粒度で分割に着手すべきか判断する必要がある。
- [ ] **組み込みシステムでの標準デザインパターン適用制約** (dp-t-005): GoFの標準的なオブジェクト指向デザインパターンを組み込みシステムにそのまま適用しようとすると、C++の継承を処理できないコンパイラや、パターン実装に必要なメモ
