# Security Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/security/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **シークレットは専用ストアに一元化しコードから排除する** (sec-p-001): 設計レビュー時、コード・設定ファイル・CI変数に生のシークレットがないかを最初に確認する
- [ ] **シークレット漏洩の検知パイプラインと対応プレイブックを常備する** (sec-p-002): 既存リポジトリ全体を TruffleHog / git-secrets / Horusec 等でスキャンし、初回は誤検知含め手動で全件確認する
- [ ] **短命トークンによるAPI認証の基本形** (sec-p-003): ユーザー認証は「資格情報→トークン交換」の形にし、以後のリクエストは Bearer トークンで行う
- [ ] **認証と認可を分離し役割別に最小権限を設計する** (sec-p-004): 設計時に認証（本人性の検証）と認可（操作可否の判定）を別の関心事として明示的に分ける
- [ ] **ゼロトラスト: 内部通信も毎回検証する** (sec-p-005): 「攻撃者はすでに内側にいる」を設計の前提に置き、境界単位でなくリソース単位で防御する
- [ ] **OSS依存は採用前にメンテ体制・スコア・ライセンスを審査する** (sec-p-006): 新規依存の追加時に OpenSSF Scorecard 等で脆弱性・メンテナンス・ビルドのリスクを確認する
- [ ] **依存の明示宣言・固定と外部ツールへのシェルアウト回避** (sec-p-007): 言語のパッケージ機構（Goモジュール等）で全依存を完全かつ正確に宣言し、ビルドが決定論的になる状態を保つ
- [ ] **入力検証とアンハッピーパスの意図的テスト** (sec-p-008): 外部から来るデータはすべて「複雑な引数」とみなし、型・値域・境界の検証とエラー処理を入口で行う（防御的プログラミング）
- [ ] **RAG・文書ストアに認可メタデータを組み込む** (sec-p-009): 文書・チャンクのメタデータに、閲覧を許可するロール・認可情報・機密区分を設計段階から含める
- [ ] **SBOMと供給網リスク管理を調達・出荷の両面で運用する** (sec-p-010): ビルドパイプラインでSBOMを自動生成し、依存の正式な記録として維持する
- [ ] **シークレットは専用ストアから実行時取得する** (sec-p-011): シークレットは集中管理型のシークレットストア（Secrets Manager / Vault 等）に置き、アプリは実行時にAPIで取得する設計を既定にする
- [ ] **シークレットの多層防御：鍵とストアの二重アクセス制限** (sec-p-012): シークレットを保護する暗号鍵（CMK等）のポリシーに「特定サービス経由の呼び出しのみ復号可」という条件（kms:ViaService 相当）を付け、鍵の用途をシークレットストアに限定する
- [ ] **ゼロトラスト＋最小権限を分離コンポーネント単位で適用する** (sec-p-013): アクセス制御はシステム境界（APIゲートウェイ）だけでなく、分離された各コンポーネント（関数・キュー・テーブル）にも適用する
- [ ] **OWASP API Top 10 を3カテゴリでレビュー観点化する** (sec-p-014): 認証認可：トークンの失効・検証、認証フローの実装誤り、ブルートフォース耐性、管理者と一般ユーザの職務分掌、権限昇格経路の有無を確認する
- [ ] **AI生成コードは「脆弱性含有率が高い」前提でレビューする** (sec-p-015): AI生成コードを人手コードと同等以上の基準でレビューする。特に頻出弱点：OSコマンドインジェクション、不十分な乱数、例外処理の不備
- [ ] **依存関係の追加・更新をアーキテクチャ上の重要決定として扱う** (sec-p-016): 新規依存の追加、メジャーバージョンアップ、ベンダー変更は影響の大きい決定として扱い、レビュー・記録（ADR等）を要求する
- [ ] **脅威モデルは生きた文書として維持し、機密として扱う** (sec-p-017): 脅威モデルを特定時点の成果物でなく、システムの変化とともに更新する有効な文書として管理する
- [ ] **データ層のセキュリティは暗号化単体でなく多層で構成する** (sec-p-018): DB保護を層で設計する：暗号化/ハッシュ化＋安全な設定＋アクセス制御＋監視＋定期更新（パッチ）の5点をレビュー項目にする
- [ ] **全アカウントへの最小権限・MFA・異常監視の基盤統制** (sec-p-019): すべてのアカウント種別（人間・サービス・アプリ）に最小権限と need-to-know を適用し、例外を残さない

## アンチパターン（該当していないか）

- [ ] **APIでのBasic認証・パスワード直渡し** (sec-a-001): レビューで Authorization: Basic を見たら、クライアント側にパスワード平文保存を強要していないかを確認する
- [ ] **既知脆弱性の未パッチ放置と設定ミスの併発** (sec-a-002): 依存とランタイムの既知脆弱性を継続的に検出し、重大CVEには適用期限つきのパッチ運用を敷く
- [ ] **XMLパーサーの外部実体参照を有効のまま使う** (sec-a-003): XMLを受け取るエンドポイントのレビューでは、パーサー設定で外部実体解決とDTD処理が無効化されているかを必ず確認する
- [ ] **コード・リポジトリへの平文シークレット混入** (sec-a-004): レビュー時に diff だけでなく、コミット履歴・.env系ファイル・ノートブック・スクリプト内のハードコード資格情報を検出対象にする
- [ ] **信頼ゾーン内の無認証通信（DMZ神話）** (sec-a-005): レビュー時、内部API・DB・キュー等への接続が「ネットワーク到達性のみ」で守られていないか確認する。到達できる＝呼べる、になっていたら要修正

## トレードオフ（明示的に判断したか）

- [ ] **横断的セキュリティをAPIゲートウェイに集約するか各サービスで持つか** (sec-t-001): 外部公開APIが複数ある場合は、ゲートウェイ層に認証・レート制限・WAF・ポリシー適用を集約するのを既定とする（一貫性と監査性が上がる）
- [ ] **脅威モデリング手法の選択: リスク定量か網羅列挙か要件化か** (sec-t-002): ビジネス影響の定量化と経営説明が目的なら、PASTA型（ビジネス目標→技術範囲→分解→脅威分析→脆弱性→攻撃列挙→リスク影響の7段階）を選ぶ
- [ ] **シークレット管理：クラウドネイティブ vs サードパーティ製品の選定** (sec-t-003): 単一クラウドで完結するなら純正サービスを優先する。プラットフォームの認証・ポリシー・監査ログ・マネージドDBとの統合が深く、運用が軽い
- [ ] **サービス間セキュリティ：アプリ内ライブラリ vs メッシュ/基盤層への委譲** (sec-t-004): 多言語（polyglot）構成では基盤層（サイドカー/メッシュ）委譲を優先する。言語ごとの証明書管理実装のばらつきと、ライブラリ未導入による意図的・偶発的なセキュリティ迂回を防げる
- [ ] **内部トラフィック暗号化：LBでのTLS終端をどこまで許容するか** (sec-t-005): 既定判断：プライベートネットワーク内のサービス間通信をHTTPにするのは広く受け入れられたトレードオフであり、一般的なアプリでは許容できる
