# Networking Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/networking/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **TCP/IPレイヤーモデルで通信障害を切り分ける** (net-p-001): 実務の切り分け単位はTCP/IPモデル（アプリケーション/トランスポート/インターネット/リンク）にする。OSI 7層は教育用の概念モデルとして扱う
- [ ] **プロトコルの実挙動はパケットキャプチャで確認する** (net-p-002): tcpdump/tsharkでキャプチャし、Wiresharkで解析する手順をプロトコル調査の標準にする
- [ ] **DNS解決の経路とキャッシュ層を把握して切り分ける** (net-p-003): 解決経路（クライアント→ローカルリゾルバ→ルート→TLD→権威サーバ）を前提に、いまどの段階の応答を見ているかを意識して調査する
- [ ] **DNSの完全性・秘匿性は明示的な保護機構で担保する** (net-p-004): 応答の出所検証・改ざん検知にはDNSSEC（ゾーンの鍵ペアによる署名）を使い、署名検証を実際に有効化する
- [ ] **高頻度の短命接続ではエフェメラルポートとTIME_WAITを設計する** (net-p-005): 接続頻度の理論上限を見積もる（TIME_WAIT 60秒なら同一2ホスト・同一宛先ポート間で60秒あたり約65,536接続）
- [ ] **TCPチューニングはシステム全体とソケット単位を使い分ける** (net-p-006): システム全体の既定はsysctl（net.ipv4.tcp_*）で管理し、変更は差分と根拠を記録する
- [ ] **TCPの内部挙動はトレースポイント優先で観測する** (net-p-007): まず安定インターフェイスであるトレースポイント（tcp:tcp_retransmit_skb、tcp:tcp_send_reset等）を使う
- [ ] **TCP性能調査は定番チェック項目を順に確認する** (net-p-008): ソケット送受信バッファの使用率、バックログキューの使用率とドロップ、輻輳ウィンドウの順に確認する
- [ ] **ソケットAPIのライフサイクルを前提に接続処理を実装する** (net-p-009): 役割を固定する: 接続を開始する側がクライアント、接続を待つ側がサーバ
- [ ] **セキュリティグループは最小権限とステートフル特性を前提に設計する** (net-p-010): 必要なアクセスだけを許可する（例: SSHはインターネット全体でなく特定IPセットに限定）
- [ ] **サービスをエッジ/バックエンドに分類してネットワークを分離する** (net-p-011): サービスを「エッジ（公開）」と「バックエンド（内部のみ）」に分類し、バックエンドはプライベートゾーンに置く
- [ ] **フローログで通信ベースラインを作り逸脱を検知する** (net-p-012): VPC・サブネット・ネットワークインターフェイスの単位でフローログを取得する
- [ ] **転送時暗号化のプロトコルバージョンを保守対象として扱う** (net-p-013): 転送時暗号化（TLS）を「設定して終わり」ではなく、更新が必要なコンポーネントとして棚卸し対象に含める
- [ ] **HTTP経路はcurlで段階的に実測検証する** (net-p-014): curl -vでステータスコードとヘッダを観察する（例: HTTP→HTTPSリダイレクトなら301が返ることを確認）
- [ ] **到達性の問題はルーティングテーブルから確認する** (net-p-015): ルーティングは宛先IPに一致する最も具体的な（最長一致の）ルートが選ばれることを前提にテーブルを読む
- [ ] **ICMPとDNSの基本ツールを最初の切り分けに使う** (net-p-016): 接続性・ルーティングの一次確認はICMP系ツール（ping等）から始める
- [ ] **トランスポートプロトコルはワークロード特性で選ぶ** (net-p-017): IP/TCP/UDP/QUICのパフォーマンス特性の違いを前提に、ワークロードに合ったプロトコルを選定する
- [ ] **コンテナ調査はネットワーク名前空間を前提に観測点を選ぶ** (net-p-018): net名前空間が見えるインターフェイス・ソケット・ルートをフィルタすることを前提に、どの名前空間から観測しているかを常に確認する
- [ ] **調査の最初期にインターフェイスを列挙し複数ネットワークを疑う** (net-p-019): ネットワーク情報収集を調査の最初期に行い、全インターフェイスと接続先ネットワークを列挙する
- [ ] **通信のレジリエンス機能はビジネスロジックの外に置く** (net-p-020): サーキットブレーカー、バックオフとタイムアウト付きリトライ、ルーティング等を「サービス間通信ロジック」として業務ロジックから分離する

## アンチパターン（該当していないか）

- [ ] **TIME_WAIT対策に安全性の低い強制リサイクルを使う** (net-a-001): まず接続再利用（コネクションプール・持続接続）で新規接続数そのものを減らす。tcp_tw_recycleは使わない
- [ ] **DNS応答を無検証で信頼する** (net-a-002): DNSSECの署名検証・DoH/DoTを有効化し、名前解決の結果だけでピアを信頼せずTLS証明書検証を併用する
- [ ] **セキュリティグループの広域開放を「あとで絞る」つもりで残す** (net-a-003): 許可は必要なIPセット・ポートに限定して追加する。SGには明示的拒否がなく広い許可は打ち消せない
- [ ] **本番で高頻度カーネル関数を全数トレースする** (net-a-004): 呼び出し回数の把握はオーバーヘッドの軽い手段（Ftraceの関数プロファイリング/funccount）を使う
- [ ] **ネットワーク層の制御にアプリレベルの精密さを期待する** (net-a-005): ネットワーク制御は広い不変量（ゾーン分離・環境分離）に使い、ビジネスロジック依存の判断はアプリ層の認証認可で実装する
- [ ] **非推奨TLSバージョンを「動いているから」と放置する** (net-a-006): 使用中のTLSバージョンを定期的に棚卸しし、非推奨バージョン（TLS 1.0/1.1）のサービスをアップグレードする
- [ ] **通信ミドルウェア（ブローカー）へのビジネスロジック集中** (net-a-007): ビジネスロジックは可能な限りブローカーの外側・マイクロサービスの内側に置く

## トレードオフ（明示的に判断したか）

- [ ] **DNSキャッシュ: 解決の速さ vs 変更反映と汚染リスク** (net-t-001): 読み取り性能重視ならキャッシュを活かし、切り替えの速さが必要なレコードはキャッシュ起因の反映遅延を計画に織り込む
- [ ] **DNS暗号化: DoH vs DoT** (net-t-002): 検閲耐性・識別されにくさ重視ならDoH（HTTPSに紛れる）、組織ネットワークの可視性・ポリシー適用維持ならDoT
- [ ] **TCP拡張（SACK/FACK）: スループット vs CPU負荷** (net-t-003): 高レイテンシ経路でスループットが必要なら有効化を検討し、CPUバウンドなホストでは効果と負荷を計測して判断する
- [ ] **輻輳制御アルゴリズム: システム既定 vs 接続単位の指定** (net-t-004): 全接続同一でよければsysctl既定で統一し、特定サービスだけ変えるならTCP_CONGESTIONソケットオプションで上書きする
- [ ] **特化カーネル構成（ユニカーネル/カーネルバイパス）: 性能 vs 運用可観測性** (net-t-005): 性能・攻撃面の利点と、SSH・シェル・既存パフォーマンスツールを失うコストを比較し、観測手段の自作コストを見積もる
- [ ] **カーネル観測: tracepoint（安定）vs kprobe（柔軟）** (net-t-006): 該当するtracepointが存在するなら常にtracepointを使い、無い情報だけkprobeで観測する
- [ ] **NACL（サブネット・広い不変量）vs セキュリティグループ（詳細契約）** (net-t-007): 組織の広い不変量はNACL、サービス間の詳細な通信契約はSGで表現し、役割分担して重ねて使う
- [ ] **負荷分散: DNSベース vs L4/L7ロードバランサ** (net-t-008): 地理分散・最寄りノード誘導はDNSリダイレクション、接続単位の即時切り離し・細かい振り分けはL4/L7 LBで行う
- [ ] **サービス間通信: 同期リクエスト/レスポンス vs 非同期イベント駆動** (net-t-009): 即時応答が必要なら同期、疎結合・多対多連携なら非同期（pub/sub）を選び、混在時は境界を明示する
