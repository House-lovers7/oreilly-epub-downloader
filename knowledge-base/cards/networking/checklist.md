## ベストプラクティス（適用を検討したか）

- [ ] **プロトコルの実挙動はパケットキャプチャで確認する** (net-p-002): tcpdump/tsharkでキャプチャし、Wiresharkで解析することで、プロトコルの実挙動（ワイヤ上のメッセージ）を確認できる
- [ ] **DNS解決の経路とキャッシュ層を把握して切り分ける** (net-p-003): 解決経路（クライアント→ローカルリゾルバ→ルート→TLD→権威サーバ）を前提に、いまどの段階の応答を見ているかを意識して調査する
- [ ] **DNSの完全性・秘匿性は明示的な保護機構で担保する** (net-p-004): 応答の出所検証・改ざん検知にはDNSSEC（ゾーンの鍵ペアによる署名）を使い、署名検証を実際に有効化する
- [ ] **TCPの内部挙動はトレースポイント優先で観測する** (net-p-007): まず安定インターフェイスであるトレースポイント（tcp:tcp_retransmit_skb、tcp:tcp_send_reset等）を使う
- [ ] **TCP性能調査は定番チェック項目を順に確認する** (net-p-008): ソケット送受信バッファの使用率、バックログキューの使用率とドロップ、輻輳ウィンドウの順に確認する
- [ ] **ステートフルな許可リスト型ファイアウォール（例: セキュリティグループ）は最小権限で設計する** (net-p-010): 必要なアクセスだけを許可し、リソースを過剰に露出させない（例: SSHはインターネット全体でなく特定IPセットに限定）
- [ ] **サービスをエッジ/バックエンドに分類してネットワークを分離する** (net-p-011): サービスを「エッジ（公開）」と「バックエンド（内部のみ）」に分類し、バックエンドはプライベートゾーンに置く
- [ ] **フローログで通信ベースラインを作り逸脱を検知する** (net-p-012): VPC・サブネット・ネットワークインターフェイスの単位でフローログを取得する
- [ ] **転送時暗号化のプロトコルバージョンを保守対象として扱う** (net-p-013): 転送時暗号化（TLS）を「設定して終わり」ではなく、更新が必要なコンポーネントとして棚卸し対象に含める
- [ ] **HTTP経路はcurlで段階的に実測検証する** (net-p-014): curl -vでステータスコードとヘッダを観察する（例: HTTP→HTTPSリダイレクトなら301が返ることを確認）
- [ ] **到達性の問題はルーティングテーブルから確認する** (net-p-015): ルーティングは宛先IPに一致する最も具体的な（最長一致の）ルートが選ばれることを前提にテーブルを読む
- [ ] **コンテナ調査はネットワーク名前空間を前提に観測点を選ぶ** (net-p-018): net名前空間が見えるインターフェイス・ソケット・ルートをフィルタすることを前提に、いまどの名前空間から観測しているかを常に確認する
- [ ] **通信のレジリエンス機能はビジネスロジックの外に置く** (net-p-020): サーキットブレーカー、バックオフとタイムアウト付きリトライ、ルーティング等を「サービス間通信ロジック」として業務ロジックから分離する

## アンチパターン（該当していないか）

- [ ] **本番で高頻度カーネル関数を全数トレースする** (net-a-004): 呼び出し回数の把握はオーバーヘッドの軽い手段（Ftraceの関数プロファイリング/funccount）を使う
- [ ] **通信ミドルウェア（ブローカー）へのビジネスロジック集中** (net-a-007): ビジネスロジックは可能な限りブローカーの外側・マイクロサービスの内側に置く

- [ ] **特化カーネル構成（ユニカーネル）: 性能・セキュリティ vs 運用可観測性** (net-t-005): ユニカーネルはCPUキャッシュヒット率向上・攻撃面縮小など性能とセキュリティの利点が見込める。ただしSSH・シェル・既存パフォーマンスツールが使えず、本番のデバッグ・チューニング手段を自前で構築する必要がある
- [ ] **負荷分散: DNSベース vs L4/L7ロードバランサ** (net-t-008): 地理分散・最寄りノードへの誘導はDNSリダイレクション（クライアント位置に応じて異なるIPを返す）が向く。DNSキャッシュにより以後のアクセスも同ノードに固定される
