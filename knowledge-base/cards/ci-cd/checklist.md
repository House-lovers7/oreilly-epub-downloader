# Ci-Cd Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/ci-cd/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。
> 2026-10-02: active カードのみ掲載（F2 昇格 16 枚＋R1 昇格 8 枚）。candidate は精査パケット output/kb-promotion/2026-10-ci-cd.md を参照。

## ベストプラクティス（適用を検討したか）

- [ ] **全コミットで自己テストビルドを走らせ、常にデプロイ可能な状態を保つ** (cicd-p-001): CIサーバーをバージョン管理に連携させ、新しいコミットやブランチごとに自動テストを実行させる
- [ ] **依存関係はコピペせず、バージョン指定で依存管理ツールから取り込む** (cicd-p-002): 外部ライブラリは依存管理ツール経由で取り込み、ソースをコードベースにコピーしない
- [ ] **デプロイパイプラインは手作業を残さず、ボタン1つで全工程が動くところまで自動化する** (cicd-p-003): コードを書く工程とレビュー以外の、自動化できる工程はすべてパイプラインに載せる
- [ ] **パイプラインのplan用権限とapply用権限を分け、plan側は読み取り専用にする** (cicd-p-004): PR作成時に走るplanステップには読み取り権限だけを渡す
- [ ] **デプロイサーバーの資格情報は長期キーでなく自動管理の短命クレデンシャル（OIDC等）にする** (cicd-p-005): 可能な限り、自動管理される短命クレデンシャル（例: OIDC）をパイプラインの認証に使う
- [ ] **パイプラインを用途別に分割して権限を最小化し、ワークフロー定義の編集も保護する** (cicd-p-006): 用途別（アプリ・DB・ネットワーク等）またはチーム別にパイプラインを分け、それぞれに必要最小限の権限だけを与える
- [ ] **パイプラインをGitOps原則（宣言的・版管理・自動pull・継続的調整）で組む** (cicd-p-007): 望ましい最終状態（構成）と、それを実現するスクリプト・API呼び出し（実装）を分け、インフラはOpenTofu等の宣言的ツール、アプリはKubernetes等の宣言的ツールで管理する
- [ ] **PRでテストとplan結果を提示してレビューし、マージでapplyを実行し、ロック待ちを設定する** (cicd-p-008): PRを開いたら、コンパイル・静的解析・単体テスト・統合テストと、実行計画（plan）の生成を自動実行する
- [ ] **ライブラリにはSemVerでバージョン付けし、破壊的変更をMAJORで利用者へ伝える** (cicd-p-009): バージョン番号をMAJOR.MINOR.PATCH形式で付ける
- [ ] **共有スタックコードをライブラリとしてバージョン管理・昇格し、ラッパースタックで環境ごとに構成する** (cicd-p-010): 共有スタックコードをライブラリとしてバージョン付けして昇格する
- [ ] **設定をコードとして外出しし、パイプライン設定をアプリコード・テストと同じ場所に置く** (cicd-p-011): 設定を標準のバージョン管理システムに保存できる形（外出しした設定）にする
- [ ] **パイプラインを複数フェーズに分け、失敗箇所がログを探さなくても分かるようにする** (cicd-p-013): テスト・ビルド・環境クリーンアップ・リポジトリ再構築など、すべてのパイプラインをフェーズ（ステージ）に分ける
- [ ] **ビルド成功のシグナルをアーティファクト生成か、マージ前のビルド成功要求で明確にする** (cicd-p-014): パイプラインの最終ステップでビルドアーティファクト（インストール手順が決まった単一のパッケージ）を作り、存在をデプロイ可の合図にする
- [ ] **統合テストもCIパイプラインで毎pushに実行し、ローカルと同じコマンドで走らせて構造化レポートを保存する** (cicd-p-015): 単体テストに加えて統合テスト（本物または模擬のインフラ・APIを使う）もCI/CDパイプラインに組み込み、push ごとに実行する
- [ ] **インフラ定義を含めあらゆるものをバージョン管理し、望ましい状態の唯一の元にする** (cicd-p-016): インフラの望ましい状態の元はすべてVCSにし、VCSへコミットされた変更がインフラ変更を決める形にする
- [ ] **ビルド・パイプラインの認証認可を、多要素認証と最小権限で定期的に見直す** (cicd-p-020): ビルドプロセスに関わるアカウントと鍵、およびそれらに紐づく権限が、多要素認証を有効にした最小権限アクセスに設定されているか
- [ ] **SBOMでコンポーネントを列挙し、透明性の一部として脆弱性・出所の情報とあわせて管理する** (cicd-p-023): ソフトウェア構築に使ったコンポーネントとサプライチェーン上の関係を記録するSBOMを作る
- [ ] **取り込むコードを信頼する前に、コードレビュー・テスト・スキャンで品質と完全性を検査する** (cicd-p-024): 依存として取り込むコード（プロプライエタリ、商用、オープンソース、ローコード／ノーコード、生成されたコード、OSとフレームワーク）が、信頼される前にどの検査（コードレビュー・テスト・スキャン）を経たかを確認できる状態にする
- [ ] **デプロイ手順書は手書きせず、自動デプロイスクリプトから毎ビルド生成する** (cicd-p-026): 自動デプロイプロセスの各ステップを、実際に入力するコマンドラインのレベルで出力するタスクをデプロイスクリプトに持たせる
- [ ] **CIでテストカバレッジを出力しアーティファクトとして公開し、テスト品質を見える化する** (cicd-p-027): CIのテストステップでカバレッジプロファイルを出力する（例: go test ./... -coverprofile=coverage.out）

## アンチパターン（該当していないか）

- [ ] **シークレットを環境変数やパイプライン設定経由で渡し、露出経路を考えない** (cicd-a-003): シークレットを環境変数で直接渡す設計を避ける。環境変数は開発者のワークステーションには適しても、パイプラインの各ステージには適さないことがある

## トレードオフ（明示的に判断したか）

- [ ] **ライブラリ分割：ソースコード依存 vs バージョン付きアーティファクト依存、単一リポジトリ vs 複数リポジトリ** (cicd-t-001): アーティファクト依存では、ライブラリ側の変更は新バージョンが公開され、利用側が明示的に取り込むまで影響しない
- [ ] **デプロイサーバーの選択：CIサーバー共用 vs 技術特化型、パイプライン定義言語の選択** (cicd-t-002): CIと同じサーバー（GitHub Actions・CircleCI・GitLab等）でデプロイも実行する案と、技術特化型（OpenTofu/Terraform用、Kubernetes用のArgo CD・Flux等）を使う案を比較する
- [ ] **スタックのパラメータをパイプライン設定に持つか（Pipeline Stack Parameters）** (cicd-t-003): パイプラインツール自体がコードで構成されていれば、パイプライン設定に置いた値もコードとしてバージョン管理できる
