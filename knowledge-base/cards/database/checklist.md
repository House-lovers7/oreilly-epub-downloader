# Database Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/database/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **レプリケーション運用は容量予測メトリクスで先手を打つ** (db-p-001): データセットサイズ、バックアップ所要時間、レプリカ復旧所要時間、復旧後に同期が追いつくまでの時間、実行中のネットワークスループット、本番ノードへの負荷影響を定常メトリクスとして収集する
- [ ] **シャード戦略はスケールが必要になる前に設計しておく** (db-p-002): 初期設計の段階で、将来のシャーディングキー候補（データを一意に識別するか意味のある部分集合に分けられるフィールド）を特定しておく
- [ ] **バックアップは「リストアできること」を継続的に検証する** (db-p-003): 特定時点へのポイントインタイムリストアが実際にできるかを定期的に演習する
- [ ] **DRサイトはプライマリと地理的リスクを分離する** (db-p-004): DRサイトはプライマリと同じ災害リスク帯（同一の災害多発地域）に置かない
- [ ] **DBスキーマ変更はCIパイプラインで自動検証する** (db-p-005): スキーマ変更のコミットごとに、ビルド・テストデータ投入・マイグレーション適用・パッケージングを自動実行するCIを構成する
- [ ] **大規模データ移行はストラングラー方式＋自動化で進める** (db-p-006): 旧システムから新スタックへ機能単位で少しずつ移す反復的アプローチ（ストラングラーフィグ）を採用する
- [ ] **インデックスは頻出クエリの述語列に絞って設計する** (db-p-007): まず実際のクエリを収集し、WHERE / JOIN / ORDER BY / GROUP BY に頻出する列を候補にする
- [ ] **アクセス頻度・可変性で列を分ける垂直パーティショニング** (db-p-008): 属性を分類する: アクセス頻度（ホット/コールド）や可変性（mutable/immutable）でグループ化する
- [ ] **トランザクション境界でエラーハンドリングを単純化する** (db-p-009): 不可分であるべき一連の更新を1トランザクションにまとめ、全成功コミットか全ロールバックの二択に落とす
- [ ] **プロキシ層で接続数制御とレプリカ負荷分散を行う** (db-p-010): DB前段にプロキシ層を置き、読み取り要求をレプリカ群へ分散させる。その際レプリカのラグ状態を見て振り分ける
- [ ] **サービス横断更新はSagaと冪等性で設計する** (db-p-011): 各サービスは自分の状態変更とロールバック後の一貫性確保に全責任を持たせ、調整役はコマンド発行と完了確認に限定する
- [ ] **正規化は冗長性排除と将来のクエリ変化への保険として使う** (db-p-012): OLTPスキーマはまず3NFを既定とする: 1NF（各列が単一値・一意な主キー）→2NF（部分従属の排除）→3NF（推移的従属の排除）の順に点検する
- [ ] **追記型ストアでは小ファイルのコンパクションを運用に組み込む** (db-p-013): 定期的なコンパクション（OPTIMIZE相当のジョブ）をパイプラインの運用タスクとして最初から計画する

## アンチパターン（該当していないか）

- [ ] **ホットシャードを固定配置のまま放置する** (db-a-001): シャード単位で負荷メトリクスを取り、偏りを検知できるようにする
- [ ] **SaaS任せのバックアップとバックアップ製品へのアーカイブ代用** (db-a-002): SaaS採用時は契約書と製品ドキュメントで、リストア可能性の保証範囲を実際に確認する（バージョン履歴やごみ箱は障害・攻撃からの保護ではない）
- [ ] **下流に伝わらないスキーマ変更（JSON柔軟性の罠）** (db-a-003): スキーマ変更（カラム追加・型変更・リネーム・意味変更）を下流の取り込みパイプライン利用者へ通知するプロセスを設ける
- [ ] **不変量保護のためのテーブル全体ロック** (db-a-004): 守るべき不変量（例: 利用可能数量は0以上）を明文化し、それを壊しうる並行操作の組を特定する
- [ ] **偏ったパーティションキーによるホットスポット** (db-a-005): キー候補ごとに実データの分布とアクセス頻度を確認してから採用する
- [ ] **自前の追記型トランザクションログを安易に本番投入する** (db-a-006): 採用するなら「単純さ・外部依存なし」という利点が本当に必要な局面（プロトタイプ、単一ノード）に限定する
- [ ] **レプリケーションやスナップショットをバックアップと同一視する** (db-a-007): バックアップの定義を「オリジナルと独立に保存され、破損時に復旧に使えるコピー」とし、この基準で構成を審査する

## トレードオフ（明示的に判断したか）

- [ ] **ACID か BASE（結果整合性）かの選定基準** (db-t-001): 残高・在庫・課金など「一時的な不整合が業務エラーになる」データはACID系（RDB等）を第一候補にする
- [ ] **非同期レプリケーション採用時の遅延とデータ損失リスク** (db-t-002): 書き込みスループットと水平スケールを優先するなら非同期を選び、レプリカは常にリーダーより遅れうる前提でアプリを設計する
- [ ] **シングルリーダーかマルチリーダーかの選択** (db-t-003): デフォルトはシングルリーダーにする。実装・運用が単純で、書き込み競合の解決が不要なため
- [ ] **ハッシュ分割かレンジ分割か：クエリパターンで決める** (db-t-004): 個別レコードをキーで引くアクセスが主体なら、決定論的ハッシュによる分割で負荷を均等化する
- [ ] **マネージドDBかセルフマネージドDBかの判断** (db-t-005): エンジン選択やカスタム構成の自由度が本当に必要な場合のみセルフマネージド（EC2等への自前構築）を選ぶ
- [ ] **データ仮想化（フェデレーション）か物理統合（ETL）か** (db-t-006): リアルタイム性が重要で、データの複製・移動コストを避けたい場合はデータ仮想化を検討する
- [ ] **パーティション粒度は細かいほど良いわけではない** (db-t-007): 粒度はクエリのフィルタ条件（最頻のプルーニング単位）に合わせて選ぶ。多くの用途では日付単位で十分
- [ ] **シャーディング導入の判断基準** (db-t-008): 導入条件は「単一マシンに収まらないデータ量」または「単一マスターの書き込み限界」に達する見込みがあること。読み取りスケールだけならレプリカやキャッシュを先に検討する
- [ ] **書き込み一貫性の実現手法: WAL・ロック・MVCCの使い分け** (db-t-009): クラッシュ耐性が主目的ならWAL（先行ログ書き込み）を持つストアを選ぶ。障害後はログ再生で一貫状態へ復元できる
- [ ] **リードレプリカ増設は線形にスケールしない** (db-t-010): 単一リーダー構成では書き込みはリーダーに集中したままなので、レプリカ増設は読み取り偏重ワークロードにのみ効く
- [ ] **キャッシュ導入は読み取りスケールと引き換えに新たな依存を作る** (db-t-011): キャッシュ追加で読み取りスケールは大きく改善するが、SLO達成が「キャッシュが生きていること」に依存するようになる点を設計に明記する
