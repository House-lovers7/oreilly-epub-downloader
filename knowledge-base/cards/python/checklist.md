## ベストプラクティス（適用を検討したか）

- [ ] **IDを持たない業務概念は frozen dataclass / NamedTuple の値オブジェクトにする** (py-p-001): データは持つがIDを持たない業務概念（注文行など）は値オブジェクトとし、@dataclass(frozen=True) で不変にする
- [ ] **業務上の失敗は専用の例外クラスで表し、pytest.raises の match まで含めて検証する** (py-p-002): 在庫切れなど、ドメインエキスパートとの会話で出てくる失敗は OutOfStock のようなドメイン例外として定義する
- [ ] **UoW は with ブロックで使い、commit しなければ変更しないデフォルトにする** (py-p-003): Unit of Work は with uow: で使い、uow.commit() を明示的に呼んだときだけ変更が確定する作りにする
- [ ] **並行更新の防止は、time.sleep で遅いトランザクションを作り2スレッドで検証する** (py-p-004): 一方の更新に time.sleep(0.2) を挟む関数を用意して、遅いトランザクションをシミュレートする
- [ ] **イベントは過去形・コマンドは命令形で名付けた dataclass にし、失敗の扱いを分ける** (py-p-005): イベント・コマンドは振る舞いを持たない @dataclass の純粋なデータ構造として定義し、共通の親クラス（Event / Command）を置く（メッセージバスの型ヒントにも使える）
- [ ] **書き込みと読み取りを分け、POST は 202 と空の結果、状態は読み取り専用 GET で返す（CQS）** (py-p-007): 書き込み用エンドポイントはデータを返さず、単純な成功ステータス（201 Created / 202 Accepted など）を返す。重要なのはステータスコードでなく、作業を書き込みフェーズとクエリフェーズに論理的に分けること
- [ ] **mock.patch の文字列は、テスト対象コードが呼んでいる名前に合わせる** (py-p-008): 足し算の結果だけを確認したいなど、一部の出力だけを検証したいとき、依存する関数（preamble()）を mock.patch("mod1.preamble", return_value="") で消す
- [ ] **入力の欠落・重複・型違い・無効値・巨大データを網羅したテストにする** (py-p-009): テストは、入力の欠落、重複、型違い、順序違い、無効値、巨大な入力・出力の各ケースが揃っているか確認する
- [ ] **一度しか使わない大きな列はリスト内包でなくジェネレータ式で処理する** (py-p-010): for で1要素ずつ処理するだけなら [n*n for n in range(N)] ではなく、角括弧を括弧に替えたジェネレータ式 (n*n for n in range(N)) にする
- [ ] **デフォルト値の有無を区別したい引数は None でなく専用のセンチネルで判定する** (py-p-011): 引数が省略されたかどうかを判定する関数では、_NO_DEFAULT = object() のようなユニークなセンチネル値をデフォルトにする
- [ ] **例外は関数内で上げ、処理は呼び出し側で行う。局所の処理だけして引数なし raise で再送出する** (py-p-012): raise 文は関数の中に置き、try/except は関数を呼び出すコード側に置く。呼び出し側のほうが例外を適切に処理できることが多い
- [ ] **新機能やバグ修正は、先に自動テストを書き、失敗することを確認してから実装する** (py-p-014): 新機能・バグ修正の PR には、その機能・修正のための自動テストを付ける。修正前（実装前）のコードでそのテストが失敗することを確認する
- [ ] **似た入力を assert で書き連ねず、サブテスト / パラメータ化テストにする** (py-p-015): エッジケースを網羅するために同じ形のテスト入力を何通りも使うときは、assert メソッドを書き連ねない
- [ ] **最適化の前にプロファイルし、仮説と測定結果に従ってボトルネックだけを直す** (py-p-016): コードの構造を変える前に、まず仮説を立て、代表的なシステムの一部を切り出してプロファイルする。結果を最適化の原動力にする
- [ ] **@profile を使うコードは、テストが NameError で落ちないよう no-op デコレータを用意する** (py-p-017): @profile を使うモジュールの先頭で、名前空間に profile が無ければ何もしない no-op のデコレータを定義する（line_profiler / memory_profiler が注入した場合はそちらが使われる）
- [ ] **CPUバウンド処理を含む async ループは、await asyncio.sleep(0) でイベントループに制御を返す** (py-p-018): CPUバウンドな処理を回すループ内に await 文が無いと、イベントループへ制御が戻らないので、await asyncio.sleep(0) を入れて保留中のタスクを処理させる
- [ ] **バッチ送信などの後始末を伴うクラスは context manager にして、終了時に確実に flush する** (py-p-020): バッチをため込んで送るクラスは __enter__ / __exit__ を実装して with で使い、__exit__ で最後の flush() を呼ぶ
- [ ] **Numba でコンパイルする関数では NumPy 配列を使い、グローバルは定数だけにする** (py-p-021): 好みのデータ構造には NumPy 配列を使う。Numba は NumPy 配列と NumPy ビューで非常にうまく動作する
- [ ] **try/except で「例外なし」の後続処理を try ブロック内に入れず、else 節に書く** (py-p-022): except の後ろに else: を置き、『例外が起きなかったときの処理』はそこに書く
- [ ] **終了処理が必要な資源は with（コンテキストマネージャ）か try/finally で確実に閉じる** (py-p-023): ファイルは with open(...) as f: で開く。ブロックを抜けるとき（例外発生時を含む）に自動で閉じられ、try/finally より3行少なく書ける
- [ ] **ライブラリや大きなコードの例外は、共通の基底クラスを持つ階層にまとめる** (py-p-024): 自作の例外は Exception（またはそのサブクラス）を継承する。組み込みの例外クラスを継承しないクラスは、多くの例外の場面で機能しない
- [ ] **型ヒントは実行時に強制されない。型の整合は mypy などの外部チェッカーで検査する** (py-p-025): 型ヒント付きの変数や関数（def get_thing() -> str: のように戻り値は矢印で書く）には、mypy（pip install mypy）を実行して型の不一致を検出する。通常の Python インタプリタは誤った型の使用を捕捉しない
- [ ] **インデックスで書き換えるループより、リスト内包表記で新しいリストを作る** (py-p-026): for i in range(len(L)): L[i] += 10 のようなパターンは、L = [x + 10 for x in L] のリスト内包表記に置き換える

## アンチパターン（該当していないか）

- [ ] **薄いはずのエンドポイントにバリデーションとオーケストレーションを書き足す** (py-a-001): エンドポイント内に is_valid_sku のような存在確認などの検査が増えてきたら、サービス層へ移す
- [ ] **グローバルなインスタンスの属性（self.queue）に処理中の状態を持たせる** (py-a-002): スレッドを使う環境で、グローバルなバスインスタンスが self.queue のような処理中の状態をインスタンス属性に持っていないか確認する
- [ ] **空の except: や except Exception: で全例外を握りつぶす** (py-a-004): except: （例外名なし）を使わない。システム終了呼び出しや Ctrl+C も例外で実現されており、通常はこれらを通したい
- [ ] **Python が自動で検出するエラーを assert で二重チェックし、assert が -O で消えることを忘れる** (py-a-005): assert は開発中にプログラムの条件（ユーザー定義の制約）を確かめる用途に使う。実プログラムの誤りを捕まえる用途ではない
- [ ] **一度しか走査できないイテレータ（zip・map・enumerate・ファイル・ジェネレータ）をリストのように再走査する** (py-a-006): enumerate・zip・map・filter・open（ファイル）の結果は自分自身がイテレータ。同じ結果から複数の走査をしない。最初からやり直すにはそのツールをもう一度呼ぶ
- [ ] **コルーチンを await せずに呼ぶ／タスク化せず await を並べて『非同期』にしたつもりになる** (py-a-007): async def の関数（コルーチン）を呼ぶだけの文を書かない。呼んでも awaitable オブジェクトを作るだけで実行されず、『coroutine ... was never awaited』の RuntimeWarning になる。await するか、asyncio.run で実行する
- [ ] **except ... as X の変数を except ブロックの後で参照する** (py-a-008): except Exception as X: の X は except ブロックの中だけで使う

## トレードオフ（明示的に判断したか）

- [ ] **継承（ABC）か合成（ラッパー委譲・Protocol）か。フェイクの保守負担との釣り合い** (py-t-002): 継承の代わりに、ラッパークラスが実体を保持して公開メソッドを委譲し、機能を足す形を検討する（chunk の例では、TrackingRepository が実体のリポジトリを保持して .add() / .get() を委譲する）
- [ ] **下位層の失敗を上位へ伝える方法: DB例外そのまま・None 返し・アプリ固有例外** (py-t-003): DB 固有の例外をそのままウェブ層で処理する案はレイヤーを混ぜるので避ける。ウェブ層は特定のデータベースについて何も知るべきではない
- [ ] **統合テストの範囲とデータベースの差し替え方（インメモリSQLite / 専用モック / 本番同種DB）** (py-t-004): A→B→C の全接続（A→B、B→C、A→C）を個別にテストすると、接合点が増えるほど数が増える。統合テストは基本的に完全なテストとし、最後のピース（ディスクへの保存）だけを差し替える案も考える
- [ ] **テスト対象の分離: mock.patch か、環境変数によるフェイクのインポート切り替えか** (py-t-005): 関数単位で依存を消すなら mock.patch を使う。特定の関数ごとにモックを書く必要がある
- [ ] **CPUバウンド処理の並列化: GIL のもとで、スレッドでなく何を選ぶか** (py-t-006): GIL あり標準ビルドの Python では、使えるコアが複数あっても一度に1つの命令しか実行されない。CPUバウンド処理をスレッドで並列化する前提を置かない
- [ ] **手作りの最適化か、ネイティブ実装ライブラリの活用か** (py-t-007): numpy など C / Fortran を包んだライブラリを適切に使えば、同程度の C コードと同じくらい速くできる。自前の最適化より先に検討する
- [ ] **asyncio.TaskGroup か asyncio.gather か（例外時の振る舞いの違い）** (py-t-008): きめ細かい例外処理が必要なとき、またはエラー時に残りのタスクをキャンセルしたいときは asyncio.TaskGroup を使う
- [ ] **非同期I/Oの同時実行数と複雑さ: 既定値に従い、実験で確かめ、自作せず成熟ライブラリを使う** (py-t-009): 書籍の一実験の結果では、同時リクエスト数を増やすと利点が減少し、250リクエストぐらいで利点がなくなった（この数値は書籍の実験条件での結果で、一般的な閾値ではない）。書籍は、実行する同時タスク数を妥当なデフォルト（最新のコンピュータでは一般に100〜200が良い賭け）にするか、アプリケーションでテストして決めるのがベストとしている
