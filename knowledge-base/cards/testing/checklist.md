# Testing Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/testing/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **テストピラミッドに沿って層別の比率を設計する** (test-p-001): 土台に多数の高速な単体テスト、中間に少数の統合・サービステスト、頂点に最小限のE2Eという比率を基本形にする
- [ ] **赤/緑/リファクタリングのリズムで実装する** (test-p-002): まず失敗するテストを書き、実際に失敗すること（かつ失敗メッセージが明確なこと）を確認してから実装に入る
- [ ] **テストの書きにくさを設計改善のシグナルとして使う** (test-p-003): テストを書こうとして依存関係やグローバル状態が邪魔になったら、テストを曲げるのではなくコード側の再設計を検討する
- [ ] **単体テストは外部依存ゼロ・ミリ秒単位で走る状態を保つ** (test-p-004): 単体テストは外部依存（DB・ネットワーク・他サービス・ファイルシステム）に接続せず、副作用から完全に分離する
- [ ] **依存を明示的に宣言し、テストではフェイクを注入する** (test-p-005): ハンドラやサービスは依存（リポジトリ、Unit of Work、通知、セッションファクトリなど）を引数やコンストラクタで明示的に受け取る
- [ ] **テーブル駆動テストでケース追加のコストを下げる** (test-p-006): 入力と期待値を構造体・マップの表として定義し、ループで各ケースをサブテストとして実行する
- [ ] **ハッピーパスと同じ重みで境界値・異常系をテストする** (test-p-007): 各機能に対し、典型ケースに加えてエッジケース（ゼロ、負値、異常に大きい値、空）のテストを必ず用意する
- [ ] **テストを種別ディレクトリで構造化しCIと対応付ける** (test-p-008): tests/unit、tests/integration、tests/e2e のように種別でディレクトリを分ける
- [ ] **タグでテストを選別しCIステージ別に実行する** (test-p-009): テストを目的別（unit / integration / perf）にタグ付けし、コンテキストに応じて選択実行できるようにする
- [ ] **統合ポイントは障害カテゴリ別にテスト方式を割り当てる** (test-p-010): 統合点ごとに障害モードを「構成」「権限」「ペイロード（契約）」に分類し、それぞれをテストでカバーするか明示的に判断する
- [ ] **トランザクション境界の挙動は実DBで明示的にテストする** (test-p-011): Unit of Work・トランザクション管理には「デフォルトでロールバックする」「例外発生時にロールバックする」の統合テストを明示的に書く
- [ ] **レガシーコードは変更前に既存挙動のテストで固定する** (test-p-012): 変更予定の機能に対し、まず現状の挙動を固定するテストを書き、全部通ることを確認してから変更に入る
- [ ] **リファクタリングは常に動く状態を保つ小さなステップで行う** (test-p-013): 「外部の振る舞いを変えずに内部構造を改善する」という定義を守り、機能追加やバグ修正と混ぜない
- [ ] **バグ修正は再現する失敗テストから始める** (test-p-014): 修正に着手する前に、バグを再現する失敗テストを書く。失敗すること自体が原因を理解している証明になる
- [ ] **AI支援コーディングはテストスイートとTDDのリズムで統制する** (test-p-015): 包括的なテストスイートを常備し頻繁に実行することを、AI活用の前提条件にする
- [ ] **インフラコードにも自動テストの階層を適用する** (test-p-016): テストの目的を「変更への自信」と捉え、ユニット→統合→E2Eの自動テスト階層をインフラコードにも構築する
- [ ] **リカバリ手順は継続的テストと予行演習で保証する** (test-p-017): リカバリを高頻度の継続的プロセスにする（新規ノード構築→リカバリ→クラスタ追加のイテレーションを日常的に回す）
- [ ] **ベンチマーク・負荷テストでも出力の正しさを検証する** (test-p-018): 負荷テストのシナリオ内でステータスコードとレスポンス内容をチェックし、「正しいものを計測している」ことを保証する

## アンチパターン（該当していないか）

- [ ] **実装の詳細に結合したテスト** (test-a-001): ユニットに入力を渡したときの出力・公開された振る舞いに対してテストを書く
- [ ] **定数・固定文字列をアサートするテスト** (test-a-002): 単体テストの本質はロジック・制御フロー・設定の検証にあると位置づけ、生の文字列一致アサートを避ける
- [ ] **E2E・統合テスト偏重の逆ピラミッド** (test-a-003): 単体テストで表現できる検証はE2Eから単体へ引き下げ、E2Eは全体結合の自信を得る最小限に絞る
- [ ] **テストのないコードのまま変更を積み続ける** (test-a-004): 触る箇所から特徴づけテスト（既存挙動を固定するテスト）を足し、変更のたびにカバレッジを積み上げる
- [ ] **価値を失ったテストを惰性で保守し続ける** (test-a-005): 長期的に価値を持たないと判断したテストは遠慮なく削除する
- [ ] **MLのテストスプリットを開発反復で使い回す** (test-a-006): 開発中の反復評価には検証（validation）分割を使い、テスト分割は最終確認まで温存する
- [ ] **AI生成テスト・コードの無検証受け入れ** (test-a-007): 生成されたテストの網羅性（エッジケース・異常系・無効入力）とアサートの正しさを人間がレビューする
- [ ] **リファクタリング中の赤を放置して次へ進む** (test-a-008): リファクタリング中にテストが壊れたら、このフェーズを終える前に緑へ戻すことを最優先する

## トレードオフ（明示的に判断したか）

- [ ] **テストの分離性・速度 vs 全体動作への自信** (test-t-001): 小さな範囲のテストは分離が良く高速だが、アプリケーション全体が動く自信は与えない
- [ ] **ドメイン層直接テスト vs サービス層経由テスト** (test-t-002): 新しい概念を設計している段階（ローギア）はドメインモデル直接のテストで細かく速いフィードバックを得る
- [ ] **テストファースト（TDD） vs テスト後書き** (test-t-003): 期待結果を定義できる通常の機能開発ではTDDを選ぶ。テスト設計の反復が設計改善そのものになる
- [ ] **テストダブル vs 実依存（どこまで本物を使うか）** (test-t-004): 単体テスト層はフェイク・スタブで完全に分離し、速度と安定性を確保する
- [ ] **フローテスト（エッジツーエッジ） vs ハンドラ分離テスト** (test-t-005): 基本は実メッセージバス・全ハンドラ連鎖を通すエッジツーエッジのテストでワークフロー全体を検証する
- [ ] **テスト配置：トップレベル集約 vs コード隣接** (test-t-006): トップレベル集約か各コードディレクトリ直下か、どちらかに統一し種別（unit/integration/full）の軸を持たせる
- [ ] **フィクスチャのスコープ：毎回リセット vs 状態持続** (test-t-007): デフォルトは関数スコープ（各テストの前に新規生成）にして、テストの独立性を守る
- [ ] **静的解析 vs 動的テストへの投資配分** (test-t-008): 静的解析は実行なしの早期フィードバック・規約強制・既知パターン検出に強く、ロジックの正しさは動的テストでしか確認できない
- [ ] **マクロベンチマーク環境 vs 本番での性能計測** (test-t-009): マクロベンチマーク環境は信頼性とフィードバック速度のバランスが良く、本番に影響を与えない
