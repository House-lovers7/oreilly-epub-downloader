# Api-Design Domain Checklist

> 由来: O'Reilly技術書からの蒸留カード（knowledge-base/cards/api-design/）。
> 各項目の詳細・出典は card_id で practices/antipatterns/tradeoffs.jsonl を引く。

## ベストプラクティス（適用を検討したか）

- [ ] **コンシューマ視点でAPIを設計し、実装を隠す抽象化を保つ** (api-p-001): 計画段階でAPIの利用者・要件・制約を整理し、利用者が達成したいワークフロー単位でリソースと操作を設計する
- [ ] **OpenAPI仕様をAPI契約として共有・公開する** (api-p-002): REST APIはOpenAPI（JSON/YAML）で構造・ドメインオブジェクト・セキュリティ要件・利用例を記述し、利用チームへ共有する
- [ ] **セマンティックバージョニングで変更の影響度を伝える** (api-p-003): MAJOR.MINOR.PATCH形式で、破壊的変更=MAJOR、後方互換の機能追加=MINOR、後方互換のバグ修正=PATCHとして運用する
- [ ] **破壊的変更の検知をAPIパイプラインに自動化する** (api-p-004): openapi-diff等の仕様比較ツールで新旧OASを比較し、後方互換/非互換を機械判定する
- [ ] **メジャーバージョンを分離し新旧並行運用で移行時間を与える** (api-p-005): /api/v1、/api/v2のようにメジャーバージョンをURLで分離し、両バージョンを並行稼働させて利用者に移行時間を与える
- [ ] **非推奨化から引退までのAPIライフサイクルを運用する** (api-p-006): 新メジャーバージョン公開と同時に旧バージョンをdeprecated宣言し、週〜月単位の移行期間を設ける
- [ ] **バージョニングは後付けせず設計初期に組み込む** (api-p-007): 外部公開APIではバージョニングをプロダクト機能として最初から計画し、バージョンの表現方法と利用者への伝達手段も併せて決める
- [ ] **認証（誰か）と認可（何ができるか）を分離して設計する** (api-p-008): 認証=呼び出し元の身元（アイデンティティ）の検証、認可=その呼び出し元に許可されたアクションの判定、と責務を分けて設計する
- [ ] **トークンは短命にしTLSと組み合わせて運用する** (api-p-009): ユーザー名/パスワードは初回認証でトークンに交換し、以後はAuthorization Bearerヘッダでトークンのみを送る
- [ ] **認可はOAuth2/OIDC/JWTの業界標準に乗る** (api-p-010): APIの認可はOAuth2（2.0/2.1）を基盤にし、Web/デスクトップ/モバイルそれぞれに適した認可フローを選ぶ
- [ ] **防御的プログラミングで入力を多層検証する** (api-p-011): リクエスト処理をバリデーション→リソース操作→リソース検索のような段階に分け、各段階でその段階に応じたエラーを処理する
- [ ] **横断的関心事はAPIゲートウェイと管理プレーンに集約する** (api-p-012): 外部クライアントとバックエンドサービスの間にAPIゲートウェイを置き、認証の集中化・アクセス制御・ポリシー適用・ルーティングを一元化する
- [ ] **OpenAPIからコード生成し契約と実装を同期する** (api-p-013): OASを情報源として、OpenAPI Generator等で利用者の言語ごとにクライアントコードを生成して提供する
- [ ] **API公開前チェックリストで実装・運用要素を網羅する** (api-p-014): 構築時に固定のチェック項目を通す（認証、認可、エラー処理、レート制限、ページネーション、モニタリングとロギング、ドキュメント）
- [ ] **HTTPセマンティクスと合意されたAPI標準に従う** (api-p-015): ステータスコード・メソッドの意味はHTTPの定義に従い、オーバーライドしない
- [ ] **チェンジログと通知チャネルで利用者に変更を伝える** (api-p-016): チェンジログを明確・完全・一貫した形式で維持し、バージョン間で何が変わったかを常に追える状態にする
- [ ] **OWASP API Security Top 10を観点にAPIセキュリティをレビューする** (api-p-017): APIの設計・開発・テスト・運用監視をDevSecOpsの一環として行い、OWASP API Security Top 10をレビュー観点として使う
- [ ] **未知のフィールドは削除せず受け流す（must-ignore規則）** (api-p-018): 理解できないフィールドは削除する代わりにそのまま透過させ、将来互換性を支える基本要素として扱う
- [ ] **APIメトリクスのラベルはカーディナリティを見積もって設計する** (api-p-019): ラベルはendpoint、method、statusのような有限で少数の値を取る次元に限定する

## アンチパターン（該当していないか）

- [ ] **バージョニング戦略を混在させる** (api-a-001): バージョンの表現手段は1つに統一する（例: URLパスのみ）。混在はリソース識別を困難にしキャッシュを妨害する
- [ ] **バージョニングを計画しないまま外部にAPIを公開する** (api-a-002): バージョニングをプロダクト機能として能動的に決定し、伝達の仕組みも含めて公開前に設計する
- [ ] **デプロイとリリースを分離せず多チームの一斉リリースに依存する** (api-a-003): APIバージョニングとライフサイクル管理を導入し、各サービスを独立してリリースできるようにする
- [ ] **カタログ化・認証・監査なしでAPIを本番投入する（野良API）** (api-a-004): 全APIを棚卸してカタログ化し、認証と監査ログを必須要件にする
- [ ] **メジャーバージョンを頻繁に上げる** (api-a-005): バージョン変更は日常イベントにしない。互換性を保つ追加的変更で要求を吸収する
- [ ] **コードとOpenAPI文書を手動で二重管理し整合チェックを持たない** (api-a-006): どちらか一方を情報源と決めて他方を生成するか、リンター等の整合性チェックをCIに組み込む
- [ ] **自アプリのワークフローをミラーしただけのAPIを公開する** (api-a-007): APIは新しいワークフローを可能にするプリミティブを提供する
- [ ] **資格情報をハードコード・平文のまま扱う** (api-a-008): 機密情報はシークレットマネージャで管理し、平文資格情報を使う認証機構は必ずTLSと併用する

## トレードオフ（明示的に判断したか）

- [ ] **REST vs gRPC（交換モデルの選定）** (api-t-001): 二者択一ではなくやり取りごとに選ぶ。判断軸はRichardson成熟度モデルと生産者・消費者間の結合度。高帯域のサービス間通信はgRPC、外部公開・互換性・デバッグ容易性重視はREST
- [ ] **API変更のアップグレード戦略** (api-t-002): 新ロケーション並行（利用者無変更・提供側保守増）、後方互換変更（利用者無変更・小変更でも壊れる注意）、破壊的変更（lockstep調整）の3択を組み合わせる前提で規則を決める
- [ ] **バージョンラベル方式：セマンティック vs カレンダー vs ハッシュ** (api-t-003): 互換性が読めるsemver、時期が読めるカレンダー、一意性のハッシュ。どれでも変更通知チャネルは別途必要
- [ ] **スペックファースト vs コードファースト** (api-t-004): spec→codeはツール成熟・生成で同期、code→specは制御重視だがエコシステムにより未成熟、両方手書きは整合チェック必須
- [ ] **API管理の導入：トップダウン vs ボトムアップ** (api-t-005): 開始時からAPI管理要件があるならトップダウン（API設計先行）、既存マイクロサービスに後付けするならボトムアップ
- [ ] **密結合ペアの同時リリース制御 vs 独立バージョニング投資** (api-t-006): 同一チーム所有で常に一緒に動くならブルーグリーン型の同時リリース、独立進化する利用者がいるならsemver+ライフサイクル管理に投資
- [ ] **エンドポイントのリリース戦略：カナリア vs ブルー/グリーン vs A/Bテスト** (api-t-007): リスク軽減はカナリア、混在状態の回避と即時ロールバックはブルー/グリーン（旧環境を一定時間保持）、バリアント比較はA/Bテスト（大トラフィック・長期間）
- [ ] **防御的プログラミングの徹底度 vs 実装の複雑性** (api-t-008): 信頼境界を越える入口では多層検証を徹底し、内部の信頼済み経路では厚みを減らして複雑性を抑える
- [ ] **ステートレス設計 vs 状態保持要件** (api-t-009): 水平スケーリングと統合容易性を取るならステートレス。ペイロード増と状態管理のクライアント移譲を明示的に設計判断する
